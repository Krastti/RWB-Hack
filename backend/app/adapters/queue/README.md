# Celery adapter — B-08 / #68

Контракт C-03 **1.0**, внутренние задачи `rwb.stage.execute.v1` и
`rwb.queue.dispatch.v1`. База: `1e5feae051a558d87c045cc3747f09840ba92e00`.
HTTP-контракт и DTO агентов не изменяются. Тесты не добавлены.

## Подключение

Установить зависимости из `backend/requirements-worker.txt`. Требуются PostgreSQL,
Redis или RabbitMQ и два реальных callable: оркестратор и обработчик восстановления.
Их передаёт композиционный модуль B-11/B-13. Фабрика намеренно не выбирает
бизнес-функции по содержимому сообщения и не содержит предметных заглушек.

Перед запуском применить миграции V1–V3, **V4 из PR #133**, затем V5 из этого PR.
V5 структурно зависит от V2; порядок V4 → V5 нужен для обычного режима Flyway:
нельзя сначала применить V5, а затем добавлять V4 без отдельного решения о миграции.
Поэтому выпуск B-08 выполняется после миграции B-07. Код B-08 не импортирует B-07.

Пример фабрики в композиционном модуле приложения:

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

from app.adapters.queue import Orchestrator, QueueConfig, RecoveryHandler
from app.adapters.queue.celery import create_worker_app


def build_worker(database_url: str, broker_url: str,
                 orchestrator: Orchestrator, recovery: RecoveryHandler):
    engine = create_engine(
        database_url, pool_pre_ping=True, hide_parameters=True,
        connect_args={"connect_timeout": 5, "options": "-c statement_timeout=10000"},
    )
    return create_worker_app(
        broker_url=broker_url, sessions=sessionmaker(engine),
        orchestrator=orchestrator, recovery=recovery, config=QueueConfig(),
    )
```

Модуль интеграции создаёт `app = build_worker(...)` с действительными адаптерами.
Далее, из каталога `backend`, если такой модуль называется `integration.worker`:

```sh
celery -A integration.worker:app worker -Q rwb.stages --concurrency=2
celery -A integration.worker:app worker -Q rwb.control --concurrency=1
celery -A integration.worker:app beat
```

`integration.worker` — имя модуля интегратора в примере, не поставляемая заглушка.
Отдельный control-worker нужен, чтобы длинные этапы не блокировали отправку команд.
При prefork фабрика очищает унаследованный пул соединений в дочернем процессе.
`Celery` result backend не используется: принятые результаты принадлежат PostgreSQL
и хранилищу артефактов, а не временному состоянию задачи Celery.

## Публичный интерфейс и постановка

`create_worker_app(broker_url=..., sessions=..., orchestrator=..., recovery=...,
config=QueueConfig(...)) -> Celery` регистрирует задачи и beat-расписание.
`app.queue_adapter` — `CeleryQueueAdapter` со следующими методами:

- `enqueue(transaction: Session, attempt_id: UUID) -> UUID` — сохранить одну команду
  для уже зарегистрированной последней pending-попытки. Повтор возвращает тот же UUID.
  Нет самостоятельного commit, публикации в брокер или увеличения номера попытки.
- `publish_due(limit=100)` — зарезервировать окно доставки и отправить UUID команд.
  Возвращает количество публикаций и ошибок брокера. Вызывается beat или внешним
  восстановителем. После ошибки команда снова доступна по истечении окна.

Регистратор попытки должен взять `Run FOR UPDATE`, проверить предметные условия,
создать `StageAttempt`, события и обновить метрики, затем вызвать `enqueue` в той же
транзакции. Все последующие авторы Run соблюдают ту же блокировку. Например:

```python
with sessions.begin() as transaction:
    # attempt уже создан здесь регистратором под блокировкой Run.
    command_id = app.queue_adapter.enqueue(transaction, attempt.id)
```

B-07 принимает команду **создания Run** до появления StageAttempt. Она не является
этой командой исполнения этапа. Мост B-11 регистрирует первую попытку и вызывает
`enqueue`; получение run_queue_jobs из #67 здесь не подменяется готовым pipeline.

## Получение и lease

Сообщение содержит только UUID команды. Worker читает Run и конкретную попытку
из БД, блокирует **Run → WorkerCommand → StageAttempt**, проверяет актуальность
попытки и атомарно выдаёт lease с `owner_token`, монотонным `generation` и сроком.
Блокировки не удерживаются во время LLM-вызовов.

При первом получении `queued → running`, `pending → running` и события C-03
фиксируются в общей транзакции. Новая StageAttempt не создаётся; метрика attempts
уже учтена регистратором. Чужой повтор при действующем lease подтверждается
без вызова callable; следующей доставкой управляет PostgreSQL-dispatch.
Завершённая, устаревшая или несуществующая команда не вызывает оркестратор.
Следующая попытка того же stage_id ждёт завершения или восстановления предыдущей
команды, даже если новая попытка уже зарегистрирована.
Ожидающий ответов Run не начинает новый этап. Отмена и окончательные состояния
не разрешают старт очередной pending-попытки.

`orchestrator(command: StageCommand, execution: ExecutionContext) -> None` получает
UUID Run/попытки/команды, stage_id, номер попытки, input_hash и contract_version.
Он загружает проверенные входы и выполняет принятый этап. Зависимости, бюджеты,
содержимое ответа, пути артефактов и checkpoint проверяет предметный оркестратор.

`execution` предоставляет:

- `lease` с идентификатором владельца, поколением и признаком восстановления;
- `heartbeat()` — продлить только действующее поколение;
- `transaction(recovery_complete=False)` — открыть SQLAlchemy Session под
  Run/command-lock и проверить fencing token и срок lease до и после предметной
  записи. Commit принадлежит контексту: прямые `Session.commit()`,
  `SessionTransaction.commit()` и `Connection.commit()` отклоняются обработчиками
  SQLAlchemy до commit. Завершение исходной транзакции через rollback/close
  не позволяет контексту принять результат. Raw DBAPI, SQL управления транзакцией
  и изменение таблицы worker_commands из callable не входят в этот интерфейс.

Оркестратор обязан сохранять принятый результат, ссылки, изменения статуса,
расход, события и намерение записи checkpoint через `execution.transaction()`.
Перед возвратом попытка должна выйти из pending/running. Иначе команда переводится
в восстановление. Успешный возврат callable подтверждается сохранением состояния
команды completed; повторная доставка после него не вызывает callable.

Внешние артефакты можно записывать неизменяемо до транзакции, но их принятие
обязательно проходит fencing в общем commit. Существующий AnalysisGraph с локальным
ArtifactStore автоматически не подключается: его приём результатов и checkpoint
должен быть согласован с этим контекстом в B-13. Иначе обходится защита от старого
worker. Новый адаптер не заявляет такую интеграцию выполненной.

## Потеря исполнения и восстановление

Heartbeat работает в отдельном потоке с отдельной сессией. Время lease берётся
из PostgreSQL. Настройки по умолчанию: lease 90 секунд, heartbeat 20 секунд,
окно повторной доставки 30 секунд, dispatch каждые 5 секунд. Heartbeat должен быть
чаще трети lease. Необходимо ограничивать таймауты БД и внешних вызовов.

Истёкший lease **не разрешает повторный вызов старой попытки**. Worker фиксирует
`WORKER_LOST`, завершает ещё running-попытку как failed и передаёт управление
`recovery(command, execution)` с отдельным lease. Ошибка callable аналогично
записывает `ORCHESTRATOR_FAILED`. Причина доступна в `execution.lease.reason_code`.
Если результат уже был принят, его успех не перезаписывается ошибкой транспорта.

Обработчик восстановления идемпотентен по command_id и сохраняет окончательное
решение через `execution.transaction(recovery_complete=True)`. В этом же commit
адаптер записывает `WorkerCommand.recovery_generation` текущего lease; попытка
уже должна выйти из pending/running. Простой возврат recovery или обычная
`transaction()` не подтверждают завершение восстановления: команда вернётся в
lost и будет доставлена снова. Маркер другого поколения не принимается.

Обработчик проверяет принятые результаты, намерение checkpoint,
отмену и бюджет. Новая LLM-попытка, если разрешена, регистрируется как N+1 с общим
учётом повторов и расхода и собственной командой; нельзя перезапускать N.
Уже принятый успех требует восстановления checkpoint без повторного LLM-вызова.
Падение самого recovery допускает повтор **восстановления**, защищённый новым
поколением. Старый recovery также теряет право писать данные.

Последний блок `transaction(recovery_complete=True)` должен сохранять реальный
результат предметного восстановления (статус, checkpoint или новую попытку с её
командой), а не быть пустым подтверждением. Адаптер фиксирует атомарность и
поколение; корректность предметного решения остаётся обязанностью B-13. Если
процесс упадёт между этим commit и завершением команды, следующий recovery
повторно проверит сохранённое решение и подтвердит его для нового поколения.

После потери lease старый внешний запрос может физически завершиться; fencing
запрещает принять его как результат текущего поколения. Exactly-once вызов
провайдера не обещается. Потенциальный расход потерянного вызова должен быть
сохранён предметным учётом, а не обнулён восстановлением.

## Надёжность доставки и откат

Команда сохраняется до публикации. Потеря брокера или отправителя приводит
к повторной отправке; сбой между отправкой и подтверждением даёт безопасный дубль.
Running-команда планируется к проверке по истечении lease; heartbeat переносит
этот срок. Поэтому потеря Celery-сообщения не скрывает зависшее исполнение.
Для LeaseBusy и ошибок БД Celery-задача возвращает `lease_busy` или
`delivery_pending` без `task.retry`: единственный планировщик повторов доставки —
`next_delivery_at` и dispatch. Повтор доставки не является новой LLM-попыткой.
Используются durable-очереди, persistent JSON-сообщения, late ack,
reject_on_worker_lost и prefetch=1 согласно
[документации Celery](https://docs.celeryq.dev/en/stable/userguide/tasks.html).

Для отката остановить beat и workers и вернуть предыдущий код. Сохранить таблицу
worker_commands до обработки принятых команд; она содержит состояние доставки
и fencing. До приёма команд V5 можно откатить удалением этой таблицы.
Lease-токены не попадают в публичные события или HTTP DTO. Тексты исключений
предметного callable не отправляются в Celery как результат.

Ошибки callable, heartbeat, записи восстановления, доставки и публикации в брокер
пишутся в служебные Python logger с traceback и command_id. Worker дополнительно
пишет run_id, attempt_id, generation и признак recovery. Ошибка записи состояния
восстановления логируется отдельно, сохраняя диагностику исходной ошибки.
