# Создание запуска — B-07 / #67

Контракты: C-01 **2.1.0**, C-03 **1.0**, профиль `web-fastapi-angular`.
База после исправлений review: `1e5feae051a558d87c045cc3747f09840ba92e00`.

`RunCreationService(repository, limits=..., profile=...)` предоставляет метод
`create_run(owner_id=..., project_id=..., idempotency_key=..., body=RunCreate(...))`.
Результат `CreationResponse` содержит `status_code` и исходное JSON-тело.
`RunCreationRepository` описывает атомарную операцию хранения; PostgreSQL-адаптер
получает фабрику сессий и реализацию `RunQueue`.

## Запуск и запрос

Перед запуском применить Flyway-миграции V1–V4. Обязательные настройки —
`DATABASE_URL` и `JWT_SECRET_KEY`. Необязательные `RUN_MAX_CALLS` и
`RUN_MAX_OUTPUT_TOKENS` переопределяют соответствующие лимиты C-05
(`profile.json`, `limits.run`): сейчас **60** вызовов и **180000** выходных токенов.
Без этих переменных прежняя конфигурация приложения продолжает работать.
Если переменная задана, она должна содержать положительное целое число;
неверное значение останавливает создание приложения до открытия соединений.
Тело запроса не задаёт лимиты. Явный `run_config=RunCreationConfig(...)`
имеет приоритет над окружением и значениями профиля.

```sh
curl -X POST "http://localhost:8000/api/v1/projects/$PROJECT_ID/runs" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: create-run-001' \
  -d '{"requirements_text":"Приложение управления парковкой","profile_id":"web-fastapi-angular"}'
```

Успех — `202` с полным объектом `Run`: `run_id`, новой `revision_id`, статусом
`queued`, лимитами, пустыми `stages`/`questions` и нулевыми метриками.
Текст требований сохраняется без удаления пробелов. Каждое новое создание
добавляет ревизию с очередным номером и SHA-256, сохраняя предыдущие ревизии.
Обновляется `Project.updated_at`. Неизменяемый вход хранится в
`run_input_snapshots`: текст, хеш, ревизия, полный профиль и версии контрактов,
серверные лимиты. Попытки этапов регистрирует исполнитель.

Фабрика приложения подключает POST и три существующих GET-маршрута:
`/api/v1/projects/{project_id}/runs`, `/api/v1/runs/{run_id}` и
`/api/v1/runs/{run_id}/events`. `PostgreSQLRunReadRepository(sessions)` реализует
`RunReadRepository` для `RunQueryService` и читает ту же БД, куда пишет POST.
Владелец проверяется в каждом SQL; Run и все его попытки загружаются одним SELECT.
История сортируется по `(created_at, id)` по убыванию, события — по `seq`
по возрастанию. Курсоры и проверка доступа остаются в существующем сервисе чтения.
В DTO попадают сохранённые вопросы, метрики, попытки и публичные данные событий.
Неверный сохранённый снимок даёт безопасный `500 INTERNAL_ERROR`.
`configure_run_creation(app, service)` и `configure_runs(app, service)`
сохраняют возможность отдельного подключения после авторизации.

## Повторы, конкуренция и ошибки

Ключ обязателен: 1–128 символов `A-Z`, `a-z`, `0-9`, `.`, `_`, `:`, `-`.
Область — `(owner_id, createRun, project_id, key)`. SHA-256 покрывает область
и JSON-тело после валидации, со значением профиля по умолчанию и стабильным
порядком полей. Пропущенный профиль эквивалентен явно указанному значению
по умолчанию. Изменение текста, включая пробелы, меняет хеш.

- Совпавший запрос возвращает сохранённые `202` и тело независимо от текущего
  состояния запуска, настроек сервера и перезапусков приложения.
- Другое тело даёт `409 IDEMPOTENCY_KEY_CONFLICT`; одновременно выполняемый
  запрос той же области — `409 IDEMPOTENCY_IN_PROGRESS` через неблокирующую
  транзакционную advisory-блокировку. Её освобождает commit/rollback PostgreSQL.
- Доступ проверяется заново и до чтения исходного ответа. Чужой или отсутствующий
  проект даёт `404 NOT_FOUND`. Ошибки входа дают `422 VALIDATION_ERROR`.
- После обработки повторов блокируется строка пользователя. Один активный
  запуск (`queued`, `running`, `waiting_for_input`, `cancelling`) во всех его
  проектах даёт `429 RATE_LIMIT_EXCEEDED`. `Retry-After` не отправляется:
  освобождение слота зависит от состояния существующего запуска, а срок
  окончания заранее неизвестен, особенно при `waiting_for_input`.
  Повтор создания имеет смысл после выхода этого запуска из активного состояния.
  В C-01 заголовок необязателен; если указан, он должен задавать секунды.
- Снимок ответа хранится отдельно в `run_creation_responses`, а его UUID —
  в `IdempotencyRecord.response_ref`. Записи не имеют TTL и не перезаписываются.
- Ошибка транзакции откатывает все записи, включая ревизию, ключ и задание.
  Валидация и отказ по лимиту не резервируют ключ. Ключ и хеш не пишутся в события.

Все будущие операции, допускающие запуск или возобновление исполнения,
должны брать блокировку пользователя перед проверкой лимита и затем блокировку
проекта/запуска. При добавлении другого автора ревизий он должен блокировать
строку проекта перед вычислением номера. Текущий адаптер использует стандартный
для PostgreSQL уровень изоляции READ COMMITTED.

## Интерфейс очереди и границы

`RunQueue.enqueue(transaction: Session, run_id: UUID) -> None` только добавляет
задание в переданную транзакцию. Самостоятельные commit и отправка во внешний
брокер здесь запрещены: иначе нельзя обеспечить общий откат.
`PostgreSQLRunQueue` сохраняет уникальную по `run_id` запись `createRun`
в `run_queue_jobs`. Запись видна исполнителю после commit и переживает остановку API.

Начальные события `run.created` (seq=1) и `metrics.updated` (seq=2) записываются
в той же транзакции согласно C-03. Оба получают `timestamp=Run.created_at`:
это начальный снимок, порядок которого задаёт `seq`. Время берётся после
ожидания блокировок и не откатывается к началу транзакции через `now()`.
Успех POST означает принятие и надёжную запись
задания. Получение/подтверждение заданий, lease, повторы доставки, запуск графа
и учёт попыток относятся к отдельному исполнителю, который здесь не реализован.
Память процесса и второй lifecycle-store не используются.

Новые автоматические тесты не добавлены по требованию пользователя.
Для отката сначала остановить приём POST и исполнителей, затем откатить код.
Не удалять таблицы V4 при наличии принятых запусков: они содержат их входы,
исходные ответы и ещё не выполненные задания. До приёма данных таблицы можно
удалить в порядке `run_queue_jobs`, `run_creation_responses`, `run_input_snapshots`.
