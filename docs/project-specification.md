# Спецификация продукта: агентский конвейер подготовки проектов

Текущее решение по стеку: [Angular/Bootstrap](angular-bootstrap-transition.md).

Статус: проектное решение команды для реализации на хакатоне.

Связанные документы: [роадмап разработки](development-roadmap.md), [критерии оценивания](evaluation-criteria.md).

## 1. Основание и границы

Источник требований — PDF «Кейс: Агентский ИИ-пайплайн полного цикла разработки корпоративных приложений» в этой папке: основной кейс, разделы 1–7 и приложение № 1.

Нужно разработать универсальный веб-сервис: клиент передает бизнес-требования, сервис запускает оркестрацию агентов и возвращает согласованный проект с исходным кодом и документацией. Парковочный помощник из приложения к ТЗ — пример входной задачи, а не единственный продукт, который умеет создавать система.

Различаем два уровня:

| Уровень | Что разрабатывает команда |
|---|---|
| Платформа | Веб-интерфейс, REST API на FastAPI, управление запусками, оркестратор, агенты, хранение результатов |
| Генерируемый проект | Анализ, архитектура, интерфейс, frontend, backend, модель данных, миграции, API и документация по конкретному запросу клиента |

Текущая итерация охватывает написание фронтенда, бэкенда и агентов. Тестирование, сканирование безопасности, сборка, контейнеризация, CI/CD и развертывание не включены в роадмап. Они остаются требованиями полного конкурсного пайплайна; их отсутствие означает неполное покрытие ТЗ, а не изменение правил конкурса. Текущий результат называется «проект подготовлен», а не «проект проверен и развернут».

Стек FastAPI выбран по указанию команды о допустимости замены технологий. В PDF указан целевой стек Angular / C# / Kotlin; сам PDF не содержит явного разрешения произвольной замены. Это отдельная исходная договоренность команды, а не цитата из ТЗ.

## 2. Цель и условия работы

Пользователь должен получить проект, который обычная продуктовая команда сможет продолжить разрабатывать. Основная бизнес-логика генерируется по запросу и сохраняет данные; ее нельзя заменять статичными экранами и фиктивными успешными ответами.

Условия:

- Единственный обязательный предметный вход — текст бизнес-требований. Технологический профиль и шаблоны задаются платформой заранее.
- Уточнения допустимы только для существенных неоднозначностей: прав доступа, безопасности, архитектуры и ключевых сценариев. Остальные решения оформляются как допущения.
- Требования заказчика, допущения и открытые вопросы хранятся раздельно.
- Каждое функциональное требование получает стабильный ID вида `FR-001`; сохраняются связи с экранами, API, сущностями и файлами.
- Анализ, контракты и код должны описывать одно поведение. Неприменимые разделы помечаются с объяснением.
- Для генерируемого web-интерфейса используется выбранный UI Kit.
- Недоступные внешние системы подключаются через документированные адаптеры и mock-сервисы. Mock не заменяет основную предметную логику.
- Артефакты сохраняются в версионируемом репозитории; для хакатона нужен экспорт в локальный GitLab.
- Записываются время, токены, обращения к модели, попытки и ручные уточнения.

## 3. Объем первой продуктовой версии

Включить:

1. Создание проекта из текста, историю проектов и запусков.
2. Анализ требований и ограниченный цикл уточнений.
3. Проектирование архитектуры, данных, API и экранов.
4. Генерацию web frontend, backend, миграций и mock-адаптеров.
5. Генерацию продуктовой, системной и пользовательской документации.
6. Просмотр прогресса, результатов этапов и расхода ресурсов.
7. Отмену запуска, возобновление после ответа пользователя и повтор неудачного этапа.
8. Скачивание снимка проекта и экспорт в GitLab по настроенному подключению.

Первая поддерживаемая конфигурация генерируемого проекта: Angular 22 + TypeScript + Bootstrap 5.3, FastAPI, PostgreSQL. Мобильная генерация Kotlin и геоданные PostGIS — отдельное расширение в роадмапе. Если это расширение не реализовано, нельзя заявлять полное выполнение парковочного кейса: мобильный интерфейс прямо требуется в приложении к ТЗ. Kafka добавляется только при предметной необходимости, а не как обязательная часть каждого проекта.

В первой версии пользователь не редактирует произвольные файлы проекта через браузер и не запускает сгенерированный код внутри платформы. Результат — исходники и документация; интерактивный предпросмотр работающего приложения требует отдельного контура исполнения за пределами этой итерации.

## 4. Пользователи и сценарий

Роль первой версии — автор проекта. Он видит только свои проекты и артефакты. Командный доступ и совместное редактирование не входят в первую версию. Техническая учетная запись GitLab настраивается отдельно и не является ролью пользователя продукта.

Основной сценарий:

1. Пользователь входит, создает проект и вставляет бизнес-требования.
2. Frontend сохраняет проект и запрашивает запуск. API возвращает `run_id` без ожидания LLM.
3. Оркестратор выполняет анализ. При критическом вопросе запуск переходит в `waiting_for_input`; пользователь отвечает в карточке запуска.
4. Архитектор фиксирует версии контрактов. После этого frontend-, backend- и документационный агенты могут работать параллельно.
5. Оркестратор собирает артефакты, формирует манифест и связи с требованиями.
6. Пользователь просматривает файлы и метрики, скачивает ZIP или экспортирует результат в GitLab.

Альтернативы: ошибка модели, исчерпание бюджета, отмена, потеря соединения браузера, конфликт экспорта. В каждом случае показываются сохраненный результат, причина остановки и доступное следующее действие. Закрытие вкладки не отменяет запуск.

## 5. Архитектура и стек

```text
Angular UI → REST /api/v1 → FastAPI → PostgreSQL
                              ↓
                         очередь заданий
                              ↓
                   worker → LangGraph → LLM adapter
                              ↓
                      хранилище артефактов
                              ↓
                       ZIP / GitLab adapter
```

| Компонент | Решение и ответственность |
|---|---|
| Frontend платформы | Angular 22, TypeScript, Angular CLI, Bootstrap 5.3/SCSS; HttpClient и RxJS для REST и опроса состояния |
| API платформы | FastAPI, Pydantic, SQLAlchemy, Flyway; OpenAPI, права, проекты, запуски, результаты |
| Данные платформы | PostgreSQL; отдельная схема данных, не общая с генерируемыми приложениями |
| Фоновые задания | Celery + Redis; API только ставит задания и читает состояние |
| Оркестрация | LangGraph внутри worker; граф этапов, контрольные точки, возобновление |
| Модели | Единый адаптер к предоставленной LLM; адрес, модель и учетные данные из конфигурации |
| Артефакты | Файловый storage adapter с заменяемой реализацией; в БД метаданные, а не крупные файлы |
| Репозиторий | GitLab adapter: создание репозитория, запись снимка, возврат commit SHA |

Миграции схемы БД платформы выполняются через Flyway: версионированные SQL-файлы
`backend/migrations/V<version>__<description>.sql`. SQLAlchemy используется для ORM.
Применённые миграции не редактируются; изменения схемы оформляются новой версией.
Flyway хранит историю и контрольные суммы в `flyway_schema_history`.

Это выбранные технологии реализации, а не обязательные условия организаторов. Версии фиксируются командой при создании зависимостей. Не требуется использовать конкретный LLM SDK: адаптер должен поддерживать фактический API предоставленной модели.

Разделение кода платформы: `frontend/`, `backend/app/api/`, `backend/app/services/`, `backend/app/models/`, `backend/app/workers/`, `backend/app/agents/`, `contracts/`, `templates/`. Каждый агент работает через общий интерфейс, не пишет в таблицы и не вызывает HTTP-обработчики напрямую.

## 6. Функциональные требования платформы

| ID | Требование | Наблюдаемый результат |
|---|---|---|
| PF-001 | Создать проект из названия и бизнес-требований | Проект имеет ID, владельца и неизменяемую версию входного текста |
| PF-002 | Запускать генерацию асинхронно | Возвращается `202` и `run_id`, длительная работа выполняется worker |
| PF-003 | Показывать этапы | Видны текущий узел, статусы, время и история событий |
| PF-004 | Запрашивать уточнения | Вопрос имеет причину, связанные FR и признак обязательности; ответ возобновляет запуск |
| PF-005 | Хранить артефакты | Доступны дерево, содержимое, тип, версия, автор-агент и checksum |
| PF-006 | Связывать результат с требованиями | Для FR указаны реализующие файлы/контракты или явный статус отсутствия реализации |
| PF-007 | Отменять и повторять работу | Сохраняются попытки; успешные независимые этапы не теряются |
| PF-008 | Ограничивать ресурсы | При лимите запуск останавливается с причиной и частичными результатами |
| PF-009 | Отдавать проект | ZIP соответствует выбранному снимку; экспорт возвращает репозиторий и commit SHA |
| PF-010 | Учитывать эффективность | Видны входные/выходные токены, вызовы, попытки, длительность, уточнения |
| PF-011 | Изолировать доступ | Чужие проекты, события и артефакты недоступны по прямым ID |
| PF-012 | Использовать внешний адаптер | Недоступная интеграция имеет контракт и явно обозначенный mock |

## 7. Frontend платформы

Экраны:

- Вход: получение пользовательской сессии, ошибки входа и истекшая сессия.
- Список проектов: название, последнее состояние, дата изменения, переход в проект.
- Новый проект: название, многострочное поле требований, ограничения длины, запуск.
- Проект: исходные требования, история запусков, создание нового запуска с новой версией входа.
- Запуск: временная шкала этапов, события, вопросы, отмена/повтор, метрики.
- Результат: дерево файлов, Markdown/JSON/code viewer, манифест, ZIP, состояние экспорта.

Для каждого экрана предусмотреть загрузку, отсутствие данных, ошибку, ограничение доступа и восстановление соединения. Кнопки заблокированы на время соответствующего запроса; повторный клик не создает второй запуск. Опрос статуса выполняется каждые 2 секунды, прекращается для терминального состояния и возобновляется после возврата соединения. Это договоренность первой версии, а не требование PDF.

Интерфейс клиента работает с backend платформы. Сгенерированный интерфейс работает с backend сгенерированного проекта; URL и учетные данные этих систем нельзя смешивать.

## 8. REST API платформы

Префикс `/api/v1`. Авторизация: Bearer JWT, проверка владельца на каждом вложенном ресурсе. Минимальная реализация входа — учетные записи с хешированными паролями и заранее созданными пользователями; публичная регистрация не обязательна. Ответы постраничные, даты в UTC ISO 8601, ID — UUID.

| Метод и путь | Назначение |
|---|---|
| `POST /auth/token` | Получить пользовательский access token |
| `GET /projects` | Список собственных проектов, `limit` и `cursor` |
| `POST /projects` | Создать проект: `name`, `requirements_text` |
| `GET /projects/{project_id}` | Проект и текущая версия требований |
| `POST /projects/{project_id}/runs` | Создать снимок входа и запуск; заголовок `Idempotency-Key` |
| `GET /projects/{project_id}/runs` | История запусков |
| `GET /runs/{run_id}` | Статус, этапы, вопросы, метрики, причина остановки |
| `GET /runs/{run_id}/events?after_seq=0&limit=100` | События после указанного порядкового номера |
| `POST /runs/{run_id}/answers` | Пакет `{answers: [{question_id, value}]}` |
| `POST /runs/{run_id}/cancel` | Запросить отмену на безопасной границе этапа |
| `POST /runs/{run_id}/retry` | Новая попытка неудачного этапа от контрольной точки |
| `GET /runs/{run_id}/artifacts` | Манифест доступных артефактов |
| `GET /runs/{run_id}/artifacts/{artifact_id}` | Содержимое или скачивание отдельного артефакта |
| `GET /runs/{run_id}/archive` | ZIP зафиксированного снимка результата |
| `POST /runs/{run_id}/exports` | Асинхронный экспорт снимка в настроенный GitLab |
| `GET /runs/{run_id}/exports/{export_id}` | Статус экспорта, URL, commit SHA или ошибка |

При создании запуска тело содержит `requirements_text` (новая версия либо исходный текст проекта) и `profile_id`. Пользователь не передает пути на сервере или произвольные команды. Профиль выбирается из разрешенного списка; бизнес-требования остаются единственным обязательным предметным входом.

Единая ошибка: `{"error":{"code":"RUN_STATE_CONFLICT","message":"...","details":{},"request_id":"..."}}`. Основные коды HTTP: `401`, `403/404` для недоступного ресурса, `409` для несовместимого состояния/ключа, `422` для полей, `429` для лимита. Начальные ограничения: название 1–120 символов, текст требований 1–100 000 символов, ответ 1–10 000 символов, `limit` 1–100. UUID и допустимые значения перечислений валидируются схемами; регулярные выражения добавляются для полей, где требуется конкретный формат.

Повтор создания с тем же ключом и телом возвращает существующий результат; тот же ключ с другим телом дает `409`. Для `answers`, `retry` и `exports` также применять ключ идемпотентности. Повтор отмены возвращает текущее состояние. Ответы принимаются только на вопросы текущей ревизии в `waiting_for_input`.

## 9. Данные и состояния

| Сущность | Основные данные |
|---|---|
| User | ID, login, password_hash, состояние учетной записи |
| Project | ID, owner_id, название, даты |
| RequirementRevision | project_id, номер версии, исходный текст, hash |
| Run | project_id, revision_id, profile_id, status, current_stage, limits, timestamps |
| StageAttempt | run_id, stage_id, attempt_no, contract_version, input_hash, status, error |
| Clarification | run_id, revision, question_id, reason, related_fr_ids, answer |
| Artifact | run_id, attempt_id, path, kind, storage_key, checksum, version, FR IDs |
| RunEvent | run_id, seq, event_type, stage_id, timestamp, публичные данные |
| ModelCall | run_id, attempt_id, model, tokens_in/out, latency, outcome |
| Export | run_id, snapshot_id, status, repository_url, commit_sha, error |
| IdempotencyRecord | owner_id, operation, key, request_hash, response_ref |

Состояния запуска: `queued → running → waiting_for_input → running → completed`. Альтернативные переходы: `queued/running/waiting_for_input → cancelling → cancelled`, `running → failed`, `running → budget_exceeded`. Из `failed` допускается явный повтор в `queued` с новой попыткой; из `budget_exceeded` — только после явного увеличения разрешенного лимита. Завершенные и отмененные запуски не изменяются: новый запрос создает новый запуск.

`completed` означает, что обязательные артефакты текущего профиля сформированы и включены в манифест. Не означает успешных тестов, сборки или развертывания. Состояния этапа: `pending`, `running`, `waiting_for_input`, `succeeded`, `failed`, `cancelled`, `skipped`; пропуск сопровождается причиной. Экспорт имеет независимый статус и не переводит подготовленный проект в ошибку генерации.

## 10. Оркестрация и агенты

Граф: прием входа → аналитик → уточнения при необходимости → архитектор → параллельно frontend/backend/документация → сборщик проекта → финальный снимок. UI-проектирование входит в архитектурный контракт до параллельной генерации. Документационный агент после сборки дополняет ссылки фактическими файлами.

| Агент | Вход | Выход |
|---|---|---|
| Аналитик | Исходный текст, ответы, регламент анализа | `requirements.json`, `system-analysis.md`, `questions.json` |
| Архитектор | Принятые требования и профиль | `architecture.json`, `openapi.yaml`, `data-model.json`, `ui-spec.json`, `generation-plan.json` |
| Frontend | UI Kit, UI spec, OpenAPI, FR | Исходники frontend, настройки зависимостей, описание экранов |
| Backend | OpenAPI, модель данных, роли, FR | Исходники FastAPI, модели, миграции, предметные сервисы, адаптеры |
| Документация | Требования, архитектура, итоговый манифест | Продуктовое описание, архитектура, руководство пользователя и разработчика, ограничения |
| Сборщик | Версионированные результаты агентов | Дерево проекта, `manifest.json`, `traceability.json`, список несогласованных частей |

Контракт вызова агента:

```json
{
  "schema_version": "1.0",
  "run_id": "uuid",
  "stage_id": "backend",
  "attempt": 1,
  "input_artifact_ids": ["uuid"],
  "contract_version": "1",
  "profile_id": "web-fastapi-angular",
  "limits": {"max_calls": 10, "max_output_tokens": 30000}
}
```

Результат: `status`, `output_artifacts`, `questions`, `assumptions`, `usage`, `diagnostics`. Каждый артефакт содержит относительный путь, тип, содержимое или storage reference, `schema_version`, FR IDs и checksum. Схемы JSON фиксируются в `contracts/agents/`; текстовые пояснения модели не заменяют структурированный результат.

Правила исполнения:

- Оркестратор управляет переходами и состоянием; модель не выбирает произвольный следующий инструмент.
- После каждого успешного узла сохраняется контрольная точка. Повтор использует тот же входной снимок и создает новую попытку.
- Worker получает lease на этап; повторная доставка задания не запускает второй активный экземпляр. Запись результата и переход состояния выполняются согласованно, устаревшая попытка не перезаписывает новую.
- Начальный лимит — не более двух автоматических повторов этапа, с отдельным учетом расхода. Ошибки входа и критические вопросы не повторяются вслепую. Таймауты и бюджеты задаются профилем.
- При изменении OpenAPI/модели данных повышается версия контракта; зависимые артефакты помечаются устаревшими. Автоматическое частичное переиспользование между разными запусками не требуется.
- Агенты не меняют чужие каталоги. Общие контракты изменяет архитектор; конфликт отправляется ему как структурированная диагностика.
- Сборщик сверяет пути, наличие обязательных результатов, версии и ссылки FR. Это обработка контрактов продукта, а не замена автоматизированного тестирования приложения.

## 11. Генерируемый проект

Минимальное дерево:

```text
docs/system-analysis.md
docs/product.md
docs/architecture.md
docs/data-model.md
docs/user-guide.md
docs/development-guide.md
docs/limitations.md
contracts/openapi.yaml
frontend/
backend/
backend/migrations/
integrations/                 # только при наличии интеграций
manifest.json
traceability.json
README.md
```

В README описать структуру, зависимости, параметры конфигурации и команды разработки. Не выдавать сгенерированную инструкцию за подтверждение воспроизводимого запуска. Отчеты тестирования и безопасности не генерируются как фиктивно успешные документы.

Системный анализ включает все разделы ТЗ: назначение, границы, роли/права, сценарии, FR/NFR, компоненты, модель данных, API, события/интеграции, ограничения входа, ошибки, критерии приемки, допущения, вопросы. Регламент организаторов подключается как отдельный шаблон; пока его нет, используется структура из PDF без заявления о соответствии неизвестному документу.

Генерируемый backend должен реализовывать сохранение данных, проверки полей, права доступа и предметные переходы состояний. Frontend вызывает его реальные API и учитывает загрузку, пустые данные, ошибки, отказ в доступе и адаптивность. Для событий, если они нужны, задаются ID, версия, время, предметная схема и правила повторной обработки.

## 12. Ограничения и защита данных в реализации

Бизнес-требования и ответы LLM считаются данными: инструкции внутри них не могут менять системные правила или получать секреты. Секреты не включаются в prompt, архив, логи и репозиторий. В интерфейсе отображаются события этапов и диагностика, а не скрытые рассуждения модели.

Запись файлов разрешена только внутри каталога конкретного запуска: запрет абсолютных путей, `..`, симлинков наружу и дублирующих конфликтующих путей. Сгенерированный код не исполняется в процессе API/worker. GitLab URL выбирается из серверной конфигурации; произвольные сетевые адреса пользователя не используются как экспортное назначение.

Лимиты запросов и одновременно активных запусков применяются на пользователя. Начальные значения профиля: один активный запуск на пользователя, максимум три обязательных уточняющих вопроса за цикл анализа; при невозможности безопасно продолжить выдавать явную причину, а не бесконечную анкету. Эти значения можно менять конфигурацией, они не являются нормами организаторов.

## 13. Условия готовности текущего объема

- Пользователь проходит путь от текста требований до скачиваемого проекта через веб-интерфейс.
- Каждый завершенный этап имеет сохраненные артефакты и метрики; сбой не уничтожает предыдущие результаты.
- Разработчики frontend и backend генерируемого проекта используют одну версию OpenAPI и модели данных.
- Основные сценарии представлены исходниками с предметной логикой, а внешние mock-интеграции обозначены явно.
- Документация показывает допущения, ограничения и непокрытые FR; неподдерживаемые платформы не скрываются.
- Результат можно экспортировать в GitLab с привязкой к неизменяемому снимку.
- UI не сообщает об успешном тестировании или развертывании, когда этих этапов нет.

Это описание ожидаемого поведения продукта, а не план тестирования.
