# Переход на Angular и Bootstrap

Решение команды от 30 октября 2026 года: frontend платформы и frontend
генерируемых web-проектов используют Angular 22, TypeScript strict,
Bootstrap 5.3 и SCSS. Backend остаётся FastAPI/PostgreSQL.

## Основа приложения

Angular CLI, standalone-компоненты, Angular Router, Reactive Forms,
HttpClient и RxJS. Оформление и layout адаптируются из
[SB Admin Angular](https://github.com/StartBootstrap/sb-admin-angular)
с сохранением MIT-лицензии. Исходный runtime Angular 11/Bootstrap 4, Pug
и демонстрационная авторизация шаблона не переносятся.
Точные версии фиксируются в package.json и package-lock.json;
Node.js 24.15+ и TypeScript 6.0.x соответствуют выбранному Angular.

F-01 (#60) создаёт интерфейс платформы. A-10 создаёт отдельный шаблон
генерируемого проекта; адреса API, токены и данные платформы в него не попадают.
F-02 (#61) отвечает за типизированный клиент; F-03–F-10 сохраняют предметные
критерии и состояния из issues. Смена библиотеки не закрывает эти задачи.

## Профиль и совместимость

Новый профиль — `web-fastapi-angular`, начальная версия 1.0.0.
Профиль описан в [C-05](../templates/profiles/web-fastapi-angular/README.md).
Переход profile_id выпущен как OpenAPI 2.0.0; текущее дополнение 2.1.0 добавляет
nullable latest_run_status в Project без N+1 запросов. Единственный допустимый profile_id и его default
заменены; HTTP-префикс остаётся `/api/v1`. Клиенты создания запусков должны
передавать новый идентификатор. Формы общих схем агентов C-02 остаются 1.0:
они допускают расширяемый profile_id. Версия предметного контракта конкретного
генерируемого приложения назначается архитектором независимо.

Persistence Run уже существует. Новые Run разрешены только с
`web-fastapi-angular`; read DTO допускает также исторический `web-fastapi-react`.
Чтение сохраняет исходный profile_id, ревизии и снимки без миграции содержимого.
A-02 обрабатывает только новый Angular-профиль; чтение старого Run не разрешает
его повторное исполнение новым профилем. Наличие пользовательских Run в чужих
окружениях не предполагается и не проверяется через production-БД.

PR #109 остаётся отдельным потребителем: его React-only control DTO требует
согласования перед подключением cancel/retry. Чистый merge не доказывает
семантическую совместимость DTO.

## Порядок внедрения

1. Обновить спецификацию, roadmap, OpenAPI, defaults аналитика и связанные
   примеры C-02 с пересчётом checksum/size_bytes.
2. Переделать профиль в PR #97 и задачи #55/#86; обновить 11 FE issues,
   сохранив зависимости, назначения и критерии продукта.
3. Создать каркас #60 и клиент #61. Затем подключать вход и проекты,
   шкалу этапов, polling, действия запусков, вопросы и анализ.
4. Выполнить `python contracts/agents/validate.py --check`, валидацию профиля,
   сборку Angular и проверки ошибок, сессии и событий. Готовность UI не означает
   готовность отсутствующих backend endpoints или полного pipeline.

Откат до принятия — возврат согласованного набора изменений через PR.
После появления запусков требуется сохранять их версию профиля и снимки.

Исторический React Run доступен в UI только для просмотра при любом статусе:
cancel, retry и отправка answers не предлагаются; обработчики также отвергают
такие команды до HTTP-запроса. Для незавершённого исторического Run интерфейс
не пытается выполнить отмену через новый профиль. При интеграции #109/#127 сервер
обязан независимо проверять профиль из сохранённого Run и возвращать 409
`UNSUPPORTED_RUN_PROFILE` без создания попытки/outbox, изменения бюджета или
переписывания frozen inputs. Проверка UI не является серверной авторизацией;
пока control write endpoints отсутствуют в main, enforcement там не реализован.
