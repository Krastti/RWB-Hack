## 2. Сквозные условия оценки

- Оценивается универсальный агентский пайплайн или значимая его часть, а не одно вручную подготовленное приложение.
- Можно выбрать полный пайплайн или специализированный участок. Отсутствие этапов не дисквалифицирует, но за них не начисляются баллы.
- Надо показать работу на выданных бизнес-требованиях, а не только заранее созданный результат.
- Используются два кейса: первый известен заранее, второй скрыт до итоговой проверки. Запуск и сборка второго выполняются непосредственно во время оценки.
- Предметный вход — только бизнес-требования; технологические шаблоны и правила допустимы заранее.
- Большая анкета обязательных вопросов противоречит ожидаемому сценарию. Оцениваются обоснованность уточнений и их влияние на результат.
- Документация, API, модель данных и код должны быть согласованы. Неприменимые разделы можно отмечать с обоснованием.
- Основной пользовательский сценарий должен работать через backend с сохранением данных. Mock допустим для обозначенных внешних интеграций.
- Проверки должны подтверждать выполнение требований. Сам факт подключения сканера или успешной сборки этого не доказывает.
- Для полного результата эксперт запускает проект из чистого окружения по инструкции без обязательной ручной правки кода; секреты не хранятся в репозитории.

## 3. Измерение эффективности

Для разработки и отладки доступ к модели предоставляется без конкурсного учета расхода. На итоговой проверке применяется отдельный демонстрационный ключ. Организаторы фиксируют:

| Показатель | Что должно быть различимо в наших данных |
|---|---|
| Входные и выходные токены | Раздельные значения по вызовам и сумма по запуску |
| Число обращений к модели | Все обращения, включая неудачные при наличии данных провайдера |
| Число повторных попыток | Автоматические повторы и явные перезапуски с сохранением истории |
| Длительность генерации | Время работы генерации отдельно от ожидания пользователя |
| Длительность полного пайплайна | От принятия входа до конечного состояния, включая паузы с отдельной детализацией |
| Итоговые статусы | Сборка, тестирование, развертывание — отдельные фактические результаты, а не вывод из успеха генерации |

Результаты могут отображаться на общем экране. Перебор большого числа решений не должен давать преимущество перед точным и экономичным процессом. Численные лимиты и формула перевода показателей в баллы в PDF не заданы. Если провайдер не возвращает usage, отмечать значение как недоступное, не подменять его нулем.

## 4. Что требуется в известном проверочном кейсе

Кейс — помощник управления платными парковками Санкт-Петербурга. Ожидаются мобильное приложение, административный web-интерфейс, backend, геоданные, API, события и документация, а для полного результата также окружение, проверки и CI/CD.

Последовательность предметного сценария:

1. Автомобиль движется по маршруту и въезжает в платную зону.
2. Система определяет зону и уведомляет водителя.
3. Водитель запускает или подтверждает парковочную сессию; видит время окончания.
4. За 10 минут до окончания появляется предупреждение.
5. При выходе или переходе в другую зону система уведомляет и предлагает проверить необходимость новой оплаты.
6. События и история сохраняются и отображаются в административном интерфейсе.

Дополнительно требуются номер и границы зоны, параметры парковки, текущий статус и оставшееся время, маршрут и история, переход в официальный сервис оплаты. Реальная оплата и промышленный доступ не требуются. Внешний поставщик заменяется adapter/mock без переписывания предметной логики.

В PDF для этого кейса перечислены Kotlin, Angular, C#/ASP.NET Core и PostgreSQL/PostGIS. Наша спецификация исходит из сообщенного командой разрешения изменить стек; это не отменяет предметные требования и мобильный сценарий. Административная web-страница сама по себе не покрывает мобильный помощник.

За тестирование/безопасность и инфраструктуру суммарно предусмотрено 25 баллов. Их исключение из текущей итерации оставляет существенную часть критериев непокрытой. При этом нельзя автоматически обещать остальные 75 баллов: они зависят от качества результата и процедуры оценки.

## 6. Материалы для экспертного просмотра

Рекомендованный комплект свидетельств, без добавления задач в текущий роадмап:

- Репозиторий пайплайна и снимок сгенерированного проекта с commit SHA.
- Исходный запрос, вопросы/ответы и зафиксированные допущения.
- Системный анализ, архитектура, API, данные и руководство пользователя.
- Трассировка FR к экранам, операциям API и файлам.
- Метрики запуска и история попыток.
- Честный список реализованных и отсутствующих этапов.
- Для этапов, если они реализованы отдельно: реальные отчеты проверок, конфигурации запуска и результаты полного цикла.

Этот перечень помогает предъявить результат; он не вводит собственную шкалу оценивания.
