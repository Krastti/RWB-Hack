# Участие в разработке RWB-Hack

Разработка ведётся по Trunk-Based Development: `main` — единственная постоянная ветка разработки. Каждый принятый набор изменений должен сохранять возможность собрать и запустить проект.

## Одна задача — один PR

Перед началом работы выберите issue с конкретным результатом и критериями приёмки. Укажите её в PR. Один PR решает одну задачу; связанные изменения документации и шаблонов допустимо включить вместе, если они описывают один процесс. Независимые изменения оформляйте отдельно.

Крупную задачу разбивайте на небольшие проверяемые шаги, каждый из которых можно безопасно принять в `main`. Например: совместимое расширение API → реализация за выключенным feature flag → подключение клиента → включение функции → удаление временного флага. Зависимости между шагами фиксируйте в issues.

## Ветки и начало работы

Создавайте ветку от актуальной `main`:

```sh
git switch main
git pull --ff-only origin main
git switch -c docs/2-contributing
```

Используйте имена `<type>/<issue>-<short-description>`:

- `feat/9-agent-task` — новая возможность.
- `fix/24-repair-limit` — исправление.
- `docs/2-contributing` — документация.
- `chore/12-ci-workflow` — обслуживание и инфраструктура.

Описание пишите латиницей через дефис. Целевой срок жизни ветки — до одного рабочего дня. Если PR не удаётся завершить в этот срок, выделите меньший безопасный шаг и зафиксируйте оставшуюся работу в issue. Долгоживущие `develop`, ветки компонентов и интеграционные ветки не используются.

Каждый агент работает в отдельном worktree или рабочем каталоге и своей ветке. Задание должно содержать issue, цель, разрешённую область изменений, базовый SHA, версию контрактов, зависимости и критерии приёмки. Изменения общих файлов согласуются через orchestrator.

## Требования и контракты

До реализации должны быть зафиксированы требования и критерии приёмки. Критичные неясности передаются пользователю и блокируют зависимые задачи; остальные решения записываются как допущения.

Параллельная реализация компонентов начинается после принятия согласованной версии контрактов в `main`: API, модели данных, событий и ролей, применимых к задаче. В PR укажите версию или SHA контрактов. Если задача их не затрагивает, отметьте это с краткой причиной.

Предпочитайте обратно совместимые изменения. Для несовместимого изменения опишите затронутых потребителей, порядок миграции и проверку совместимости; пересогласуйте контракт до запуска зависимых задач.

## Незавершённые функции

Незавершённую возможность можно принять за выключенным по умолчанию feature flag, через заглушку или совместимое расширение, если обычный путь работы остаётся исправным.

Для временного механизма укажите в PR:

- Имя, значение по умолчанию и способ переключения.
- Ответственного и issue на удаление.
- Условие удаления и проверки включённого и выключенного поведения.
- Влияние на API, данные и откат.

Флаг не заменяет проверки и не должен оставлять неработающий путь по умолчанию.

## Подготовка PR

Открывайте PR в `main` по [шаблону](.github/pull_request_template.md). Пока изменение не готово к review, используйте Draft.

Перед передачей на review:

1. Проверьте diff и исключите несвязанные изменения, секреты и случайные артефакты.
2. Сопоставьте результат с каждым критерием issue.
3. Выполните проверки затронутых компонентов и потребителей общих контрактов.
4. Заполните описание поведения, контрактов, проверок, рисков и отката.
5. При продвижении `main` обновите ветку согласно принятому в команде способу и повторите проверки результата интеграции. Конфликты разрешает автор изменения с учётом контрактов.

Укажите точные команды, проверенный SHA и результаты. Для документации достаточно проверки содержания, относительных ссылок и форматирования. Для кода применяйте релевантные build, lint, unit, integration, API/contract, E2E и security checks. Миграции проверяйте с нуля и поверх предыдущей принятой схемы.

Репозиторий находится на начальном этапе: наличие этого документа не означает, что CI и защита ветки настроены. Пока соответствующие проверки не подключены, явно указывайте выполненную локальную проверку и ограничения. Не отмечайте отсутствующую, пропущенную или упавшую проверку как успешную. Значимое непроверенное поведение блокирует готовность PR.

## Review и слияние

Для принятия PR нужны:

- Выполненные критерии приёмки и подтверждающие результаты.
- Все настроенные обязательные checks для актуального результата интеграции.
- Минимум одно одобрение другого reviewer после существенных изменений.
- Разрешённые замечания, описанные риски и применимый способ отката.

Автор не заменяет независимое review собственным одобрением. Если reviewer пока нет, PR остаётся открытым до review.

Слияния выполняются через squash merge в `main`. Заголовок PR должен объяснять результат изменения. После слияния удалите удалённую ветку и освободите рабочий каталог, предварительно убедившись, что в нём нет нужных несохранённых изменений.

При конкурентных PR используйте merge queue, если она настроена. Иначе ответственный за интеграцию последовательно обновляет базу каждого PR, проверяет результат слияния и только затем сливает. Успех проверки старого SHA не подтверждает новый результат интеграции. Прямые изменения `main`, force push в неё и обход обязательных checks не допускаются.

## Ошибки и Repair Agent

При FAIL сохраните SHA, ссылку на check, логи и категорию причины: код, контракт, миграция, инфраструктура или нестабильная проверка. Неизвестную причину передайте на разбор.

Исправление выполняет ответственный агент в той же ветке и PR с релевантным контекстом. После изменения повторяются затронутые и обязательные проверки. Допускаются максимум две автоматические попытки repair на задачу; после двух неуспешных попыток автоматический цикл останавливается и требуется решение человека. Перезапуск orchestrator не сбрасывает счётчик и не разрешает merge.

## Восстановление main

Если обязательная проверка `main` или работоспособность принятого изменения нарушены:

1. Зафиксируйте инцидент: сломанный SHA, симптомы, логи и последний известный исправный SHA.
2. Приостановите обычные слияния и deploy. Разрешён только PR для восстановления.
3. Назначьте ответственного. Подготовьте минимальное исправление либо revert проблемного изменения через PR. Не переписывайте историю `main`.
4. Для миграций и внешних эффектов отдельно оцените обратимость: revert кода не гарантирует восстановление данных. При необходимости примените согласованное компенсирующее изменение.
5. Проведите review и обязательные проверки восстановления, затем squash merge.
6. Возобновите очередь и deploy только после успешных обязательных checks на новом SHA `main` и smoke test затронутого сценария. Оставшиеся PR обновите относительно исправленной базы.
7. Приложите к инциденту результат восстановления и создайте отдельные issues для оставшихся причин.

## Документация и выпуск

Изменение поведения, конфигурации или API сопровождайте актуальной документацией в том же PR. Выпуск должен ссылаться на конкретный SHA `main`, проверенные артефакты и результаты проверок. Инструкция запуска должна позволять воспроизвести результат из чистого окружения.
