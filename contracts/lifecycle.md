# C-03: жизненный цикл запуска, этапов и событий

Версия документа и event payload: **1.0**. Статус: **предложение для review**.
Задача: [#53](https://github.com/Krastti/RWB-Hack/issues/53).
Основание: §8–10 [спецификации](../docs/project-specification.md),
[OpenAPI платформы](platform.openapi.yaml), принятый [C-02](agents/README.md)
и [CONTRIBUTING.md](../CONTRIBUTING.md). Проверенный upstream:
`3d3a2a88cd7e859885c78956df657d2a198528f2`.

Это контракт для B-05/B-06/B-07/B-08/B-09/B-10/B-12, графа A-04 и интерфейса
прогресса. Здесь определяются допустимое поведение и согласуемые решения,
а не заявляется наличие работающих сервисов, очереди, checkpoint или CI.
HTTP DTO остаются в OpenAPI; agent envelope — в C-02. При расхождении интерфейсов
публичный Metrics следует OpenAPI: числовые поля не заменяются null. Преобразование
неизвестного внутреннего usage без потери его смысла определено в разделе 10.

## 1. Единицы состояния и неизменяемые данные

- **Run** — один запуск по неизменяемому снимку требований, профилю и принятым
  версиям контрактов. Новый бизнес-текст создаёт новую ревизию и новый Run.
- **Логический этап** определяется `(run_id, stage_id)`. Его актуальное состояние
  берётся из последней попытки; план ещё не запущенного этапа не является попыткой.
- **StageAttempt** — зарегистрированная попытка исполнения: внутренний UUID,
  run_id, stage_id, attempt_no, contract_version, input_hash, status и времена.
  В API это StageAttempt; `attempt_no` соответствует `AgentInput.attempt` C-02.
  Внутренний UUID соответствует `Artifact.attempt_id`, а не номеру attempt_no.
- **Checkpoint** — ссылка на согласованно сохранённое состояние графа, входы,
  принятые артефакты и версии. Состояние процесса worker или история браузера
  не являются checkpoint. Его внутренний формат определяет A-04 (#78).
  Checkpoint ускоряет восстановление, но может отсутствовать на момент POST
  или оказаться недоступным после сбоя. Источник истины — сохранённые данные Run,
  попытки, входы, ответы, принятые артефакты и события; отсутствие checkpoint
  само по себе не запрещает восстановление по этим данным.

Уникальны `(run_id, stage_id, attempt_no)` и `(run_id, seq)`. Номера попыток
строго возрастают внутри логического этапа; повтор доставки задания их не меняет.
Плановое pending-состояние будущего узла без StageAttempt не расходует попытку.
Регистрация настоящей pending-попытки резервирует её номер и учитывается в метриках,
даже если до вызова модели она будет отменена или завершится ошибкой проверки входа.

Input hash, ссылки и contract_version фиксируются перед исполнением. Для
обычного retry они остаются прежними. Ответ пользователя создаёт новый входной
артефакт анализа с прежним текстом и подтверждёнными ответами. Изменение
предметных контрактов требует новой версии, проверки совместимости и явного
переисполнения зависимых этапов; старые результаты не объявляются актуальными.

Принятые AgentResult, входы и байты артефактов не переписываются. Исправление
создаёт новую попытку/артефакт. Управляющее состояние ещё исполняющейся попытки
может меняться только по таблице ниже.

### 1.1. Задача плана и узел исполнения

`stage_id` идентифицирует отдельный узел исполнения, а не тип агента или общую
фазу работ. В принятом generation-plan каждый task_id и каждый stage_id уникален:
одной задаче соответствует один узел. Несколько задач одного исполнителя
получают разные stage_id; исполнитель определяется owner_agent через разрешённый
сервером реестр агентов, а не угадывается по имени stage_id.

| task_id | stage_id | owner_agent | depends_on |
|---|---|---|---|
| implement-auth | backend-auth | backend | [] |
| implement-orders | backend-orders | backend | [implement-auth] |

Это пример идентификации, не готовый generation-plan: полный план также содержит
входные references, непересекающиеся области выходов и FR IDs. Одинаковый
owner_agent не означает общую попытку, lease или счётчик retry. В простом примере
C-02 task_id=stage_id=owner_agent=backend допустимы, потому что задача всего одна;
из этого нельзя выводить обязательное равенство этих полей.

Перед исполнением orchestrator проверяет план, профиль, версии и разрешённых
исполнителей и сохраняет неизменяемое соответствие task_id → stage_id → owner_agent
в рамках Run. depends_on ссылается на task_id; готовность узла проверяется по
соответствующим stage_id зависимостей, принятым результатам и checkpoint.
Дублирующий stage_id отклоняется до регистрации попыток. Для каждого вызова
AgentInput.stage_id берётся из выбранной задачи, input_artifact_ids — из её
проверенных входов, а attempt назначается внутри этого узла. Worker получает
тот же сохранённый план/маршрут; ответ обязан повторить stage_id вызова.
Добавлять task_id в закрытые AgentInput/AgentResult DTO не требуется: задача
однозначно находится по stage_id в принятом плане Run. Свободные поля ответа
модели и совпадение имён не являются основанием для выбора исполнителя.

## 2. Состояния Run

Набор в точности совпадает с OpenAPI RunStatus.

| Состояние | Значение | Автоматическое исполнение |
|---|---|---|
| queued | Запуск принят и надёжно поставлен в очередь либо принят повтор | Ещё не исполняется |
| running | Orchestrator выполняет/планирует этапы; отдельный LLM-вызов может пока не идти | Разрешено в пределах лимитов |
| waiting_for_input | Достигнут безопасный барьер, опубликована текущая ревизия обязательных вопросов | Приостановлено до ответа или отмены |
| cancelling | Намерение отмены записано; активные попытки доходят до безопасной границы | Новые задания и LLM-вызовы запрещены |
| completed | Обязательные результаты профиля приняты и включены в зафиксированный snapshot | Завершено |
| cancelled | Отмена завершена, принятые частичные результаты сохранены | Завершено |
| failed | Продолжение остановлено из-за ошибки; автоматические меры исчерпаны или неприменимы | Только явное решение о retry |
| budget_exceeded | Для следующей необходимой работы недостаточно разрешённого бюджета | Только явное увеличение лимита и retry |

`completed` и `cancelled` — окончательные неизменяемые состояния. Новый запрос
для них создаёт новый Run. `failed` и `budget_exceeded` — состояния остановки:
для UI они завершают автоматический опрос, но поддерживают явно разрешённое
возобновление того же Run. Закрытие вкладки не является отменой.

`current_stage` — необязательная подсказка текущей фазы. При параллельных узлах
единственная строка не описывает все активные работы: UI читает `stages` и события.

### 2.1. Разрешённые переходы Run

| Из | В | Условие и обязательный эффект |
|---|---|---|
| нет записи | queued | Авторизованное создание, snapshot входа, idempotency record, run.created и надёжное намерение постановки в очередь |
| queued | running | Worker получил право исполнения; вход/профиль/версии проверены |
| running | waiting_for_input | Есть required-вопрос без answer; приняты частичные артефакты и ревизия; активные вызовы достигли безопасной границы |
| waiting_for_input | running | Атомарно принят пакет всех обязательных ответов текущей ревизии и запланирована новая попытка анализа |
| running | completed | Выполнены все условия раздела 8; нет активных/неразрешённых обязательных работ |
| running | failed | Ошибка блокирует продолжение; автоматический retry запрещён либо исчерпан; активные работы остановлены/сохранены |
| running | budget_exceeded | Следующая обязательная работа не укладывается в бюджет; частичные результаты и расход сохранены |
| queued | cancelling | Принята отмена, новые задания запрещены |
| running | cancelling | Принята отмена, новые задания запрещены |
| waiting_for_input | cancelling | Принята отмена без получения ответов |
| cancelling | cancelled | Все активные исполнения завершены/отсечены, безопасные результаты и управляющее состояние сохранены |
| failed | queued | Явный POST /retry, сохранены намерение восстановления и новая попытка; успешные независимые этапы сохранены, наличие checkpoint не обязательно |
| budget_exceeded | queued | Явный POST /retry с достаточным увеличением исчерпанного лимита, проверкой политики и новой попыткой |

Другие переходы запрещены и для команды возвращают `409 RUN_STATE_CONFLICT`.
Повтор команды, уже применённой с тем же ключом идемпотентности, возвращает
сохранённый ответ по разделу 6. Повтор cancel — отдельный допустимый no-op.
No-op не создаёт статусного события, попытки, расхода или нового seq.

Ошибка проверки входа worker сразу после получения queued сначала фиксирует
получение исполнения (`queued → running`), затем `running → failed` без LLM.
Так не вводится дополнительный переход queued → failed, отсутствующий в спецификации.

## 3. Состояния этапа и StageAttempt

Допустимы только значения OpenAPI: `pending`, `running`, `waiting_for_input`,
`succeeded`, `failed`, `cancelled`, `skipped`.

| Из | В | Причина |
|---|---|---|
| нет записи | pending | Зарегистрирована новая попытка с уникальным номером и входным snapshot |
| pending | running | Получен lease, fencing token и подтверждено право исполнения |
| pending | failed | До исполнения обнаружен неверный вход, несовместимый контракт, невосстановимые данные либо недостаточный бюджет; одно отсутствие checkpoint не является ошибкой |
| pending | cancelled | Отмена до исполнения, вызовов модели нет |
| pending | skipped | Профиль/условие делают узел неприменимым; причина обязательна |
| running | succeeded | Результат прошёл schema, references, права путей и проверки профиля |
| running | waiting_for_input | Принят валидный результат с нерешёнными обязательными вопросами |
| running | failed | Ошибка модели, контракта, бюджета, инфраструктуры или срока исполнения |
| running | cancelled | Исполнение остановлено на безопасной границе по принятой отмене |
| running | skipped | Агент вернул обоснованную неприменимость узла |

`succeeded`, `failed`, `cancelled`, `skipped` и сохранённый результат
`waiting_for_input` закрывают **этот вызов агента**. После результата выставляется
finished_at; у не начатой попытки started_at отсутствует, не подменяется датой
регистрации. При ответе пользователя создаётся попытка N+1, а предыдущая
waiting_for_input остаётся в истории. При retry failed-попытка также не
возвращается в running: создаётся новая pending-попытка.

Таким образом логический этап может пройти waiting_for_input → pending → running
или failed → pending → running, но это смена последней попытки, не переписывание
старой строки. Отмена Run в ожидании не требует превращать сохранённый
waiting_for_input AgentResult в другой результат. UI учитывает Run.status и историю.
Run.stages сохраняет историю попыток, включая причины и номера; для текущего
представления выбирается максимальный attempt_no каждого stage_id. Порядок
сериализации истории — stage_id, затем attempt_no по возрастанию; хронологическая
лента интерфейса строится по seq событий, а не по порядку этой группировки.

### 3.1. Применение C-02 AgentResult

| AgentResult.status | StageAttempt | Последующее действие orchestrator |
|---|---|---|
| succeeded | succeeded | Сохранить принятый результат и состояние; обязательно сохранить checkpoint после успешного узла, затем запускать готовые зависимые узлы; completed только после общего барьера |
| waiting_for_input | waiting_for_input | Сохранить вопросы/артефакты и перейти к безопасному барьеру уточнения |
| failed | failed | Классифицировать причину; автоматический retry, failed либо budget_exceeded по правилам ниже |
| cancelled | cancelled | Ожидаем при принятой отмене; без неё — диагностировать неожиданную остановку, не считать успехом |
| skipped | skipped | Причина обязательна; пропуск обязательного результата не разрешает completed |

AgentResult не переводит Run самостоятельно. Невалидный JSON, schema/version,
run/stage/attempt, references, checksum, чужие артефакты и недопустимые пути
дают failed с безопасной диагностикой; model usage сохраняется независимо от
приёмки содержимого. Stale-результат не применяется к актуальной попытке.

## 4. Согласованность, lease и гонки

Сервис переходов B-06 проверяет ожидаемое состояние и поколение исполнения,
затем в одной транзакции БД сохраняет новое состояние, события, ссылки принятых
артефактов, счётчики, данные/намерение восстановления и idempotency record.
Конкретный механизм блокировки/CAS — ответственность реализации; частично
видимое применение запрещено. Долгие LLM-вызовы не выполняются внутри транзакции БД.

После каждого успешного узла обязательно сохраняется checkpoint, как требует
спецификация проекта. Это не обещание общей транзакции БД и внешнего
checkpoint-хранилища: worker может записать checkpoint позже фиксации результата
в БД, но до запуска зависимых узлов и завершения Run. Намерение записи сохраняется
надёжно; при сбое запись возобновляется по сохранённым данным без повторного
LLM-вызова успешного узла. Восстановление без checkpoint — аварийный путь,
который не отменяет обязательную запись. Пока запись не выполнена, зависимые
узлы и completed заблокированы; исчерпание лимитов восстановления приводит
к failed с безопасной диагностикой по общим правилам ошибок и retry.
Checkpoint связывается с версией состояния и уже принятыми артефактами.
До использования проверяются Run, версия, input hash и
актуальность; отставший checkpoint дополняется сохранённой историей, а не
откатывает принятые ответы/результаты. Недоступный или несовместимый checkpoint
не используется: восстановление идёт по сохранённым данным раздела 5.1.

Очередь публикуется через надёжное намерение/outbox либо сопоставимый механизм.
После 202 перезапуск API/worker не должен терять принятое задание. Успешный POST
гарантирует сохранение принятой команды и её идемпотентности, **не наличие
готового checkpoint и не успешное исполнение worker**. Повтор доставки
опирается на ту же StageAttempt; уникальный lease не позволяет двум workers
одновременно владеть одним поколением. Простой mutex в памяти недостаточен.

Истёкший lease не даёт права считать старый ответ актуальным. Старое поколение
отсекается fencing token. Если исполнение потеряно, причина WORKER_LOST фиксируется
и восстановление проходит как контролируемая новая попытка с общим учётом retry.
Exactly-once применение результата не означает exactly-once запрос к внешней LLM:
повторный сетевой запрос и его возможный расход должны учитываться отдельно.

При конкуренции cancel/ответ/результат/ошибка порядок задаётся фиксацией в БД:

1. Если cancelled/completed уже зафиксирован, новый управляющий переход запрещён.
2. Если первым принят cancel, сохраняется cancelling: запоздалый успех/ошибка
   не превращает Run в completed/failed/budget_exceeded. Учитывается фактический
   расход, валидные результаты текущего ещё разрешённого исполнения можно
   сохранить как частичные; затем безопасный барьер ведёт в cancelled.
3. Если первым принят финальный результат, cancel возвращает текущее состояние
   без изменения. Если первым принят ответ, последующий cancel отменяет уже
   возобновлённую работу; новый LLM-вызов допускается только до записи намерения отмены.
4. При ошибке/вопросах/бюджете блокируются новые зависимые задания. Уже активные
   независимые вызовы достигают безопасной границы; их валидные результаты и usage
   сохраняются. В waiting_for_input/failed/budget_exceeded нет активного исполнения.

Терминальный snapshot фиксируется после сведения активных исполнений. Потерянный
сетевой ответ помечается неизвестным расходом, а не нулём. Ответ старого поколения
не переписывает ни snapshot, ни финальные метрики; последующее выяснение расходов
может храниться отдельным аудитом, без изменения закрытого Run.

## 5. Уточнения и ревизии вопросов

Формат вопроса — C-02/OpenAPI Question: question_id UUID, question, reason,
required, related_fr_ids и необязательный answer. `required=true` — критичный
вопрос; отсутствие ответа представляется отсутствием answer, не null/пустой строкой.
Вопросы без required не блокируют запуск; безопасные решения отдельно записываются
в assumptions. Начальное ограничение — три обязательных вопроса за цикл анализа
по профилю, а не новый лимит JSON Schema. Нельзя обходить его бесконечной цепочкой
одинаковых вопросов: граф учитывает историю и при невозможности продолжить
останавливается с понятной причиной, не запускает бесконечную анкету.

questions_revision=0 означает, что вопросов ещё не публиковали. Публикация
нового набора вопросов увеличивает ревизию в пределах Run;
неизменный набор сохраняет UUID и ревизию. Принятие ответа не переименовывает
вопрос и не создаёт новую ревизию автоматически. История прошлых наборов и
ответов сохраняется; в Run.questions виден текущий набор, который может содержать
ранее отвеченные вопросы. Артефакт анализа сохраняет UUID прошлых вопросов по C-02.

POST /answers принимает **один пакет всех ещё не отвеченных обязательных
вопросов текущей ревизии**, с возможными ответами на её необязательные вопросы.
Пакет не применяется частично. Порядок проверок:

1. Авторизация и владение Run; чужой/несуществующий ресурс — одинаковый 404.
2. Idempotency-Key и hash нормализованного тела; повтор ранее принятого пакета
   возвращает сохранённый ответ даже после выхода из waiting_for_input.
3. Для новой операции Run должен быть waiting_for_input, ревизия — текущей;
   иначе 409 RUN_STATE_CONFLICT.
4. Неизвестные/повторные UUID, пустые/пробельные значения, длина более 10 000
   и неполный обязательный пакет — 422. Уже подтверждённый ответ не заменяется
   другим значением; изменение исходного решения оформляется новым входным Run.
5. Атомарно сохранить ответы, вход возобновления/его неизменяемую ссылку,
   N+1 pending-попытку, событие answers.accepted, переход Run в running и надёжное
   намерение возобновления. Готовый checkpoint для этого POST не требуется;
   worker выбирает способ восстановления при исполнении.

Ключи вопроса в API — UUID. Локальные Q-001 из аналитика 0.1 напрямую не подходят:
нужно постоянное отображение по [плану миграции](agents/MIGRATION.md).
При возобновлении FR IDs и исходный текст не меняются из-за нового номера попытки.
Новые факты из ответов получают evidence.source=answer; модель не подставляет
подтверждение за пользователя. Бюджет проверяется до следующего обращения к модели;
принятый ответ не теряется, даже если затем Run остановится по лимиту.

### 5.1. Восстановление прерванного waiting_for_input

Технический обрыв браузера, API, worker или checkpoint-хранилища не равен
POST /cancel. Ожидание не требует удерживать живой worker или lease. Состояние,
текущая ревизия, вопросы, уже принятые ответы и ссылки на результаты сохраняются
надёжно, чтобы после перезапуска восстановить тот же Run, а не начать новый анализ.

| Момент обрыва | Как продолжить |
|---|---|
| До фиксации вопросов/перехода | Незакоммиченные изменения не публикуются; восстанавливается последний принятый шаг, потерянное активное исполнение обрабатывается по правилам lease/retry |
| После фиксации waiting_for_input, до записи checkpoint | Из БД восстанавливаются ревизия, вопросы, ответы и артефакты; Run остаётся в ожидании, повторный LLM-вызов и новый набор вопросов не нужны |
| Браузер закрылся или потерял сеть во время ожидания | GET Run и чтение событий с сохранённого курсора восстанавливают экран, включая уже отвеченные вопросы |
| POST /answers не был зафиксирован | Run продолжает ожидать; клиент повторяет пакет с тем же Idempotency-Key |
| Ответы приняты, но HTTP-ответ потерян | Replay того же POST возвращает сохранённый результат; ответы, счётчик уточнений и pending-попытка не создаются повторно |
| Ответы приняты, но worker/очередь прервались до продолжения | Outbox/восстановитель находит принятое намерение и доставляет то же задание; worker восстанавливает состояние без повторного запроса уже принятых ответов |

Worker сначала ищет совместимый checkpoint. Если его нет, восстанавливает
состояние из зафиксированного снимка требований/профиля, истории попыток,
принятых артефактов, questions_revision и подтверждённых ответов. При этом
сохраняются FR/question IDs, номера попыток, seq, расход и счётчик автоматических
повторов. Успешные независимые этапы не выполняются заново. Повторная доставка
уже зарегистрированной команды не является новой попыткой.

Если обязательные ответы ещё не приняты, восстановление возвращает граф к
ожиданию без перехода Run в running. Если они уже приняты, продолжается ранее
созданная pending-попытка. Восстановитель проверяет недоставленные команды и
зависшие исполнения; при потерянном уведомлении повторно доставляется то же
сохранённое намерение, а не создаётся ещё одна попытка. Курсор и состояние
браузера не являются условием серверного возобновления.
Новый публичный endpoint /resume не вводится:
пользователь отвечает через /answers, а восстановление принятой работы выполняет
сервер. Для уже остановленного failed используется существующий POST /retry.

Если ни checkpoint, ни сохранённых данных недостаточно или отсутствуют нужные
артефакты, нельзя молча повторять завершённые этапы или выдумывать ответы.
До принятия новой команды возвращается безопасная ошибка 500
RESUME_STATE_UNAVAILABLE без частичных эффектов. Если команда уже принята
и Run находится в running, worker сохраняет диагностику этой причины и
переводит Run в failed; после восстановления данных доступен явный retry.
Случай не относится к простому отсутствию checkpoint при целых данных Run.
Явно отменённый cancelled Run этой процедурой не возобновляется.

<!-- example: Answers -->
```json
{
  "questions_revision": 2,
  "answers": [
    {
      "question_id": "20b5ce33-5873-4796-a47d-4ce79578e101",
      "value": "Удаление запрещено всем ролям."
    }
  ]
}
```

## 6. Отмена, retry и идемпотентность

POST /cancel не требует Idempotency-Key по текущему OpenAPI. Для queued,
running и waiting_for_input записывается cancelling и запрещается новая работа.
Для cancelling повтор возвращает его текущее состояние. Для completed,
cancelled, failed и budget_exceeded операция — no-op с текущим Run и HTTP 200;
она не добавляет отсутствующие в таблице переходы. Отмена — не удаление входов,
checkpoint, истории и безопасно сохранённых артефактов.

Безопасная граница — до внешнего вызова либо после его завершения/дедлайна и
фиксации результата/неизвестного расхода. Мгновенное физическое прекращение
работы provider не обещается. Отзыв lease и fencing не позволяют старому ответу
продолжить граф. До cancelled нельзя планировать новое исполнение.

POST /retry требует Idempotency-Key. Для failed принимается явное намерение
повтора: worker использует совместимый checkpoint, если он есть, либо сохранённые
данные Run по разделу 5.1. POST не обязан найти или создать checkpoint до ответа.
Для budget_exceeded дополнительно нужно увеличение исчерпанного лимита.
Другие состояния дают 409. Нельзя менять
текст, профиль или предметные контракты через retry. Успешные независимые этапы
сохраняются; повторяются выбранный неуспешный этап и необходимые неполученные
зависимые результаты. Подмена входов успешных этапов не является безопасным reuse.

Автоматический retry отличается от POST /retry: пока исчерпываются разрешённые
автоматические меры, Run остаётся running; failed StageAttempt сохраняется,
создаётся N+1 и retry.scheduled. В Run.failed автоматический цикл уже остановлен.

Автоматический retry допускается только при безопасной retryable-диагностике,
том же входе/контракте, доступном бюджете и разрешении политики. Ошибки входа,
неразрешённый critical-вопрос, конфликт контракта и исчерпание бюджета не
повторяются вслепую. `Diagnostic.retryable` — условие, а не команда модели.

Не более **двух автоматических повторов логического этапа**: исходное исполнение
плюс максимум два автоматических. Счётчик хранится по Run/stage, атомарно
увеличивается с регистрацией повтора и не сбрасывается при worker restart,
повторной доставке или ручном retry. Ручной повтор — отдельное решение человека,
с отдельным событием; он не открывает новый автоматический лимит. Новые бизнес-
требования/явно новый Run не должны создаваться orchestrator для обхода ограничения.

Для создания Run, answers и retry область Idempotency-Key включает владельца,
операцию и ресурс. Нормализованный hash тела хранится до применения эффекта.
Тот же ключ и тело возвращают сохранённый ответ без нового события/очереди/attempt;
тот же ключ и другое тело дают 409. Авторизация проверяется и для replay.
Ключи и токены не публикуются в RunEvent. Внешний HTTP 202 означает надёжно
принятую операцию, а не успешный вызов модели.

Пример retry.scheduled после принятого ручного POST /retry, пока checkpoint
не найден/не создан. Событие не обещает, какой способ восстановления выберет worker:

<!-- example: Event -->
```json
{
  "run_id": "3a92fd8d-80d8-4b0e-a8de-8c9f8de4e101",
  "seq": 70,
  "event_type": "retry.scheduled",
  "stage_id": "analysis",
  "timestamp": "2026-10-30T12:05:00Z",
  "data": {
    "schema_version": "1.0",
    "mode": "manual",
    "previous_attempt_no": 2,
    "next_attempt_no": 3,
    "reason_code": "MANUAL_RETRY"
  }
}
```

## 7. Бюджет и сроки

Run.limits.max_calls и max_output_tokens задают совокупные разрешённые пределы
Run по всем этапам и попыткам. AgentInput.limits C-02 — выделенная часть этих
пределов для текущего исполнения, ограниченная профилем и остатком Run.
Параллельные workers резервируют бюджет атомарно; выдавать каждому полный
исходный остаток запрещено. timeout и ограничения вопросов задаются серверным
профилем: текущий публичный Limits DTO содержит только два поля бюджета.

Перед LLM-вызовом резервируются один call и верхняя граница выходных токенов;
requested max_output_tokens не превышает выделенного резерва. Известный реальный
usage сверяется с ним; неиспользованный резерв можно освободить. При неизвестном
usage резерв консервативно сохраняется, не считается нулевым расходом. Учёт
резерва для допуска следующей работы и фактические метрики — разные величины.
При нулевом остатке выходных токенов не создаётся AgentInput с
max_output_tokens=0: это нарушило бы C-02. Отказ фиксируется до вызова агента/LLM.

Недостаточный остаток до вызова не создаёт ModelCall. Текущая попытка фиксирует
безопасную причину отказа, Run проходит running → budget_exceeded. Превышение,
уже обнаруженное в ответе provider, также сохраняет фактический известный usage
и блокирует продолжение. Достижение лимита само по себе не мешает completed,
если больше обращений не требуется и итоговый snapshot уже удовлетворяет профилю.

Повтор из budget_exceeded принимает полный объект Limits по текущему OpenAPI:
оба поля положительны, ни одно не уменьшается, исчерпанный предел увеличивается
и разрешает следующую работу с учётом уже израсходованного/зарезервированного.
Проверяется политика пользователя и один активный Run; превышение разрешений
не обходится большим числом в запросе. Отсутствие необходимого увеличения — 409,
ошибка формы — 422, ограничение допуска сервиса — 429, без частичных эффектов.

Дедлайн отдельного LLM-вызова не равен дедлайну этапа. Таймаут фиксируется
нормализованной диагностикой LLM_TIMEOUT; полный срок этапа и lease контролирует
worker. Возврат checkpoint не сбрасывает общий расход и автоматические повторы.

<!-- example: Retry -->
```json
{
  "limits": {
    "max_calls": 12,
    "max_output_tokens": 60000
  }
}
```

<!-- example: AgentResult -->
```json
{
  "schema_version": "1.0",
  "run_id": "3a92fd8d-80d8-4b0e-a8de-8c9f8de4e101",
  "stage_id": "analysis",
  "attempt": 2,
  "contract_version": "1",
  "status": "failed",
  "output_artifacts": [],
  "questions": [],
  "assumptions": [],
  "usage": {
    "calls": 0,
    "input_tokens": 0,
    "output_tokens": 0,
    "duration_seconds": 0,
    "model_calls": []
  },
  "diagnostics": [
    {
      "code": "BUDGET_EXCEEDED",

      "severity": "error",
```

Это пример отказа **до** нового обращения. Нулевой calls/usage этой попытки
не означает обнуление расхода предыдущих попыток Run.

## 8. Условия completed и окончательного snapshot

Orchestrator переводит Run в completed только после всех проверок:

1. Все обязательные узлы профиля succeeded; skipped допустим только для
   неприменимого узла с причиной и без потери обязательного результата.
2. Нет активных попыток, намерения отмены, нерешённых обязательных вопросов
   или блокирующей диагностики. Отдельный успех агента этого не подтверждает.
3. Артефакты приняты по C-02, принадлежат Run, версии согласованы, отсутствуют
   конфликты путей, references разрешены, checksum/размер проверены по байтам.
4. Обязательные файлы профиля присутствуют. Traceability содержит каждый FR
   с файлами либо явным partial/unimplemented и объяснением; отсутствие основной
   предметной реализации не скрывается формальным заполнением документов.
5. Сборщик подтвердил полноту подготовки профиля, зафиксировал manifest с
   readiness=prepared и неизменяемый snapshot. Блокирующие незавершённости
   не позволяют completed; частичный snapshot остаётся partial.
6. Snapshot, финальные счётчики, Run.completed и соответствующие события
   фиксируются согласованно с данными БД. Внешний checkpoint не является
   обязательным условием завершения. Манифест не включает собственный checksum.

`completed` означает **«проект подготовлен»**. Это не результат build, тестов,
security scan, запуска или deploy. Соответствующие PASS-состояния не выводятся
из завершения генерации. Экспорт — отдельная операция со своим статусом по API;
его ошибка не переводит завершённый Run в failed и не меняет snapshot.

## 9. RunEvent и публичная история

RunEvent сериализуется как **OpenAPI Event** без переименования полей.

| Поле | Тип и правило |
|---|---|
| run_id | UUID своего Run, обязательно |
| seq | Целое ≥ 1, уникальное и строго возрастающее внутри Run |
| event_type | Непустой тип из каталога ниже; новые типы вводятся совместимо |
| stage_id | Необязательный идентификатор; обязателен по C-03 для stage/retry/usage событий |
| timestamp | Серверное время фиксации UTC ISO 8601 с Z; не источник порядка |
| data | Объект публичных данных; schema_version=1.0 обязателен для каталога C-03 |

Состояние и события записываются одной согласованной операцией. Seq выделяется
под блокировкой/сопоставимым атомарным механизмом; `MAX(seq)+1` без защиты и
локальный счётчик worker недопустимы. Перезапуск не сбрасывает seq. Пропуски
допустимы, но порядок закоммиченных событий не может инвертироваться: событие
с меньшим seq не должно становиться видимым после уже выданного большего.

Нет требования глобального порядка между разными Run. Повтор публикации
того же сохранённого события использует тот же seq. Клиент устраняет дубли
по `(run_id, seq)`, сортирует по seq и не восстанавливает порядок по timestamp.
Статусный no-op не порождает событие. Фактический новый ModelCall — отдельный
учётный факт даже при идентичном тексте ответа.

### 9.1. Каталог data версии 1.0

Во всех строках дополнительно обязательно data.schema_version="1.0".
UUID, attempt_no, FR IDs и diagnostic имеют типы C-02; reason_code — безопасный
непустой код причины, не raw exception. Snapshot/checkpoint IDs — references,
не пути на сервере. Это предложение начального каталога, не новый enum OpenAPI.

| event_type | Обязательные поля data | Когда фиксируется |
|---|---|---|
| run.created | status=queued, revision_id UUID, profile_id | Принят новый Run |
| run.status_changed | from RunStatus, to RunStatus, reason_code | Каждый действительный переход из таблицы Run |
| stage.status_changed | attempt_no ≥ 1, from StageStatus или null, to StageStatus, contract_version, reason_code | Создание/переход попытки; null → pending только для новой записи |
| questions.published | questions_revision ≥ 1, questions полный массив Question, artifact_ids UUID[] | Зафиксирован снимок ревизии; включает уже отвеченные вопросы с answer, не только новые/неотвеченные |
| answers.accepted | questions_revision ≥ 1, answered_question_ids UUID[], input_artifact_id UUID | Пакет ответов применён один раз |
| retry.scheduled | mode=automatic или manual, previous_attempt_no, next_attempt_no, reason_code; checkpoint_id UUID необязателен | Зарегистрирована новая попытка; отсутствие checkpoint_id не препятствует восстановлению по сохранённым данным |
| budget.updated | previous_limits Limits, limits Limits, reason_code | Принято разрешённое изменение бюджета |
| usage.updated | attempt_no ≥ 1, usage объект C-02 | Сохранена накопленная usage данной попытки |
| metrics.updated | metrics объект OpenAPI Metrics, tokens_complete объект с boolean tokens_in и tokens_out | Согласованный числовой снимок метрик Run и признаки полноты токенов |
| artifact.accepted | attempt_no ≥ 1, artifact metadata C-02 | Принят неизменяемый артефакт |
| snapshot.prepared | snapshot_id UUID, readiness=prepared или partial, artifact_ids UUID[] | Согласованно зафиксирован snapshot |

usage.updated — **накопленный снимок попытки**, не дельта для повторного сложения.
Для агрегации ModelCall уникален по call_id; один и тот же вызов в повторном
usage.updated не учитывается дважды. Failed/timeout-вызовы не исключаются.
metrics.updated публикуется при изменении учётных счётчиков/полноты, включая
начало вызова с ещё неизвестным usage; это снимок Run, не дельта. Изменение только
elapsed не требует события на каждый тик. Дополнительные поля находятся внутри
открытого Event.data, не добавляются к закрытым Run/Metrics DTO.

questions.published — полный снимок набора, не команда сбросить ответы. В нём
допустимы required/необязательные и уже отвеченные вопросы; наличие сохранённого
answer не отменяет required, но снимает блокировку именно этого вопроса.
Сервер объединяет вопросы с уже подтверждёнными ответами по question_id;
новый ответ модели не может очистить либо заменить подтверждённый answer.
Принимать решение об ожидании нужно по условию `required=true` **и** отсутствию
answer. Один только факт публикации не переводит Run в waiting_for_input.
UI сопоставляет question_id/ревизию, сохраняет заполненные ответы и предлагает
действия для ещё не отвеченных вопросов. Повтор публикации неизменного снимка
не создаёт ревизию, новую попытку или новый факт ручного уточнения.
Версия data позволяет расширять каталог, не добавляя поля к закрытому Event DTO.
Клиент сохраняет курсор и игнорирует неизвестный event_type/неподдерживаемую
версию data, показывая состояние из GET /runs/{id}. Неизвестный тип не является
разрешением применить произвольную команду.

История событий API доступна только владельцу Run после проверки доступа.
В questions.published этой истории разрешены полные значения answer как часть
снимка Question; answers.accepted содержит только идентификаторы и ссылку на
артефакт по каталогу выше. Эти ответы не публикуются в общей ленте или
операционных логах. В событиях запрещены prompt, chain-of-thought, raw provider
response, секреты, lease tokens, stack trace и Idempotency-Key. Разрешение answer
не разрешает включать секреты в артефакты или события. Data используется только
как данные, не вставляется в HTML и не исполняется как команда.

### 9.2. Курсор и восстановление соединения

GET /runs/{id}/events?after_seq=N&limit=L возвращает по возрастанию только seq>N,
L в диапазоне 1–100. next_after_seq — последний seq страницы, для пустой
страницы — исходный N. has_more означает наличие следующих видимых событий
после этой страницы; это не обещание отсутствия будущих событий.

Клиент сохраняет курсор после обработки страницы. При разрыве соединения
повторяет запрос с последним обработанным after_seq; повторная доставка безопасна.
По C-03 нет удаления/перенумерации истории в живом Run; если retention понадобится,
сначала нужен отдельный контракт устаревшего курсора, а не молчаливый пропуск.

При completed/cancelled/failed/budget_exceeded UI дочитывает историю до
has_more=false, затем останавливает polling до новой команды. waiting_for_input
не относится к этим состояниям: пока страница активна и сеть доступна, статус
и события опрашиваются каждые 2 секунды, как в спецификации. Ответ в другой
вкладке, серверное восстановление или отмена не должны оставлять экран навсегда
в устаревшем ожидании. После answers/retry/cancel состояние перечитывается сразу.

После возврата сети, перезапуска браузера или повторного открытия страницы
сначала запрашивается актуальный Run и восстанавливается его текущая ревизия
вопросов с answer, затем дочитываются события с последнего обработанного курсора.
Если курсор потерян, можно читать историю с after_seq=0. Данные старой ревизии
из браузера не затирают серверные ответы. Новый Run не наследует курсор старого;
после ручного retry того же Run seq продолжается.

Пример ответа при after_seq=40: ревизия 2 содержит один новый неотвеченный
и один ранее отвеченный обязательный вопрос. Это фрагмент истории, не её начало.

## 10. Метрики: область, единицы и неизвестные значения

Источник истины — сохранённые ModelCall, StageAttempt, принятые ответы и времена
переходов. Метрики не суммируются повторно из доставленных очередью сообщений.
Повторы/паузы не обнуляют счётчики; значения не выдаются за результаты невыполненных
build/test/deploy. Все числа в примерах ниже иллюстративны, а не замеры продукта.

| Величина | Семантика |
|---|---|
| model_calls | Число уникальных фактически начатых обращений к модели, включая ошибки/таймауты; отказ до обращения даёт 0 новых calls |
| tokens_in / tokens_out | Неотрицательные целые суммы **известных** значений отдельных вызовов по OpenAPI; неизвестные значения в сумму не включаются, её полнота передаётся отдельно |
| attempts | Число уникальных зарегистрированных StageAttempt всех этапов; одно исполнение после ответа или retry даёт новую попытку, повтор доставки — нет |
| manual_clarifications | Число уникальных question_id с впервые принятым непустым ответом; это не число HTTP-пакетов и не число показанных вопросов |
| duration_ms | Полное elapsed время Run от created_at до текущего момента либо последней остановки/завершения, включая ожидания и очереди |
| usage.duration_seconds | Длительность одной попытки C-02 без последующего ожидания человека; не сумма wall-time всего Run |
| model_calls[].duration_seconds | Время отдельного обращения; сумма может превышать elapsed при параллельных обращениях |

Для failed/budget_exceeded duration_ms фиксируется на момент остановки. При
явном retry elapsed снова считается от исходного created_at и включает паузу
до retry. Для completed/cancelled время фиксируется окончательно. Для текущих
queued/running/waiting_for_input/cancelling elapsed продолжает расти.
Интервалы очереди, ожидания пользователя и исполнения сохраняются отдельно
в истории; они позволяют объяснить elapsed, а не восстановить его из токенов.
Секунды C-02 переводятся в миллисекунды явно; duration_ms — не сумма длительностей
параллельных попыток. Server clock не должен давать отрицательные длительности.

Публичный Metrics следует OpenAPI без исключений: tokens_in, tokens_out,
model_calls, attempts, manual_clarifications и duration_ms всегда являются
неотрицательными целыми числами, поля не пропускаются и не заменяются null.
Внутренний C-02 usage сохраняет null, когда provider не сообщил число токенов.
Это разные представления: API показывает числовые счётчики, а не заменяет
неизвестные факты внутреннего учёта вымышленными нулями.

<!-- example: Metrics -->
```json
{
  "tokens_in": 100,
  "tokens_out": 200,
  "model_calls": 1,
  "attempts": 1,
  "manual_clarifications": 0,
  "duration_ms": 2000
}
```

### 10.1. Преобразование C-02 в OpenAPI Metrics

Решение C-03: приоритет у существующего **OpenAPI Metrics**, его схема не
расширяется до nullable. Для каждого направления токенов:

1. По уникальным call_id суммируются только полученные числовые значения.
   Пустая сумма равна 0: это счётчик известных токенов, не оценка неизвестного вызова.
2. tokens_complete.tokens_in/tokens_out равны true, если у всех начатых вызовов
   соответствующее значение известно; при нуле вызовов оба признака true.
   Активный вызов без usage и завершившийся вызов с null дают false.
3. Внутренние null и исходные ModelCall сохраняются. Дополнение пришедшего usage
   учитывается один раз по call_id, а не повторным сложением всего снимка попытки.
4. Счётчики и признаки полноты публикуются вместе в metrics.updated. При создании
   Run публикуется начальный снимок. Одни и те же числовые суммы с изменившейся
   полнотой также требуют нового события; статический Run/Metrics DTO не меняется.

Например, один вызов сообщил 100/200 токенов, второй завершился без usage:
API вернёт tokens_in=100, tokens_out=200, model_calls=2, а оба признака полноты
будут false. Это известная часть расхода, а не утверждение, что второй вызов
потратил 0 токенов. Если ни один из двух не сообщил usage, числовые суммы будут
0 с false. Для бюджета по-прежнему действует консервативное резервирование
раздела 7; известная сумма не используется как полный расход для снятия лимита.

UI применяет пару metrics/tokens_complete из одного metrics.updated. До получения
такого снимка либо при неизвестной версии событий полнота считается неизвестной;
нельзя выводить из наличия числа, что сумма окончательная. При false/неизвестной
полноте показывается «известно …, расход неполный», без самостоятельного пересчёта
неизвестного usage в 0. После возврата сети дочитываются события. Признаки живут
в открытом Event.data, не добавляются как новые поля к закрытому Metrics.

<!-- example: Event -->
```json
{
  "run_id": "3a92fd8d-80d8-4b0e-a8de-8c9f8de4e101",
  "seq": 43,
  "event_type": "metrics.updated",
  "timestamp": "2026-10-30T12:00:04Z",
  "data": {
    "schema_version": "1.0",
    "metrics": {
      "tokens_in": 100,
      "tokens_out": 200,
      "model_calls": 2,
      "attempts": 2,
      "manual_clarifications": 0,
      "duration_ms": 4000
    },
    "tokens_complete": {
      "tokens_in": false,
      "tokens_out": false
    }
  }
}
```

Пример metrics.updated — отдельная иллюстрация неполного usage, не продолжение
сценария вопросов из EventPage. Независимо от полноты все поля вложенного metrics
соответствуют действующему OpenAPI Metrics.

C-02 также допускает AgentInput.limits.max_calls=0 как внутренний сигнал
отсутствия остатка, но публичный Run.limits.max_calls по OpenAPI ≥1. В API
передаётся разрешённый общий предел Run, а не нулевой остаток; это не требует
добавлять 0 в публичный Limits.
