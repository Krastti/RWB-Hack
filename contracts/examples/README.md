# C-04: примеры ответов для экранов платформы

Задача: [#54](https://github.com/Krastti/RWB-Hack/issues/54).
Версия набора и формата каталога: **1.0**. Контракты: [C-01 / OpenAPI
2.1.0](../platform.openapi.yaml), [C-03 / события 1.0](../lifecycle.md).
Исходный SHA: `f030c71e01d8aade0a9c11e0da9708db0ec94cf0`.
Указанная в issue версия 2.0.0 дополнена совместимым полем
`Project.latest_run_status` из текущего контракта 2.1.0.

Это статические договорённости для разработки Angular/Bootstrap-интерфейса,
независимые от UI-библиотеки. Они не подключены к штатному API и не заменяют
бизнес-логику. Текущий профиль во всех запусках — `web-fastapi-angular`.
Примеры не подтверждают готовность runtime или полного pipeline.

## Файлы и экраны

Каждый файл ниже содержит непосредственно JSON-тело ответа, без дополнительной
обёртки, HTTP-заголовков и полей для UI. HTTP-статус, запрос и DTO перечислены
в машинно-читаемом [index.json](index.json). Название DTO разрешается как
`#/components/schemas/<schema>` в OpenAPI. Сам index — метаданные набора,
а не ответ какого-либо HTTP-эндпоинта.

| Файл | HTTP / DTO | Экран и назначение |
|---|---|---|
| [project-empty.json](project-empty.json) | 200 / Project | `/projects/:id`: проект создан, запусков ещё нет; `latest_run_status=null` |
| [runs-empty.json](runs-empty.json) | 200 / RunPage | `/projects/:id`: пустая история, предложение начать запуск |
| [run-running.json](run-running.json) | 200 / Run | `/runs/:id`: активный анализ, таймлайн и действие отмены |
| [events-running.json](events-running.json) | 200 / EventPage | Лента активного запуска; известный вход и пока неизвестный выход LLM |
| [run-waiting-for-input.json](run-waiting-for-input.json) | 200 / Run | `/runs/:id`: обязательный и необязательный вопросы, причина и связанные FR |
| [events-waiting-for-input.json](events-waiting-for-input.json) | 200 / EventPage | Публикация вопросов, переход к ожиданию и метрики |
| [run-failed.json](run-failed.json) | 200 / Run | `/runs/:id`: остановка после таймаута, успешный анализ сохранён, доступен явный retry |
| [events-failed.json](events-failed.json) | 200 / EventPage | Неуспешная попытка архитектуры, причина остановки и неполный usage |
| [error.json](error.json) | 409 / Error | Ошибка действия: попытка retry завершённого Run; показать message и request_id |
| [run-completed.json](run-completed.json) | 200 / Run | `/runs/:id`: подготовленный результат, успешные этапы, конечные метрики |
| [events-completed.json](events-completed.json) | 200 / EventPage | Готовность снимка, завершение и окончательные метрики |

## Семантика сценариев

- Пустой проект уже содержит исходную ревизию требований с SHA-256 текста;
  «пустой» означает отсутствие запусков, а не отсутствие обязательных полей.
  Пустая история — `{items: [], next_cursor: null}`.
- Четыре запуска — независимые сценарии с разными `run_id` и ревизиями одного
  проекта, а не последовательные переходы единственного Run. Пустой проект
  показан до их появления. Общий `owner_id` — вымышленный пользователь.
- Все UUID и числа иллюстративны. Времена — UTC с `Z`. Попытки упорядочены
  по `(stage_id, attempt_no)`, их `contract_version="1"` соответствует C-02.
  Необязательные отсутствующие поля опущены, обязательный nullable-курсор
  возвращается как null. Не добавляйте UI-поля к закрытым HTTP DTO.
- В waiting_for_input блокирует только вопрос с `required=true` без `answer`.
  Ответы ещё не приняты, поэтому `manual_clarifications=0`. Отправка использует
  `questions_revision=1`, те же question_id и контракт Answers; после успеха
  нужно перечитать Run. Ошибка stale-ревизии не означает принятие ответов.
- Failed Run приходит с HTTP 200: запрос чтения успешен, но сама генерация
  остановлена. Его `StageAttempt.error` сохраняет внешнюю обёртку `error`.
  Отдельный error.json иллюстрирует HTTP-ошибку команды, а не состояние Run.
- `duration_ms` — elapsed от created_at до updated_at в этих снимках. При
  running/waiting_for_input время продолжает расти; при failed/completed оно
  зафиксировано. Число попыток включает неуспешную архитектуру и сборку без LLM.
- Completed означает подготовку обязательных артефактов и снимка, без утверждения
  об успешных тестах, сборке зависимостей, deploy или экспорте. Манифест и байты
  файлов загружаются отдельными artifact/archive API; этот набор не подменяет их.

## События и использование

EventPage-файлы — хвосты независимых журналов после `after_seq=40`, не журналы
с начала запуска. Предыдущие события и связанные артефакты опущены. В каждой
странице seq начинается с 41, next_after_seq равен последнему seq, has_more=false
означает отсутствие следующей страницы в момент чтения; будущие события допустимы.
Следующий опрос использует возвращённый next_after_seq, а не снова 40.

Run и соответствующая страница событий согласованы по run_id, состоянию,
вопросам и последнему снимку метрик. `data.schema_version="1.0"`; внешние
stage_id присутствуют у событий этапов. Поля payload следуют каталогу C-03.
Пара `metrics` и `tokens_complete` из одного metrics.updated применяется вместе:
значение 0 при неполном usage не доказывает отсутствие расхода. После получения
изолированного Run без событий полнота токенов неизвестна.

Для локального просмотра прочитайте нужный JSON как DTO из текущего OpenAPI,
например из корня репозитория:

```sh
python3 -m json.tool contracts/examples/run-waiting-for-input.json
```

В локальном preview интерфейса передайте пару `run-<state>.json` и
`events-<state>.json` соответствующему экрану; экран проекта использует пару
project-empty.json/runs-empty.json. Подключение фикстур к production API,
дополнительная mock-служба, тесты и изменения схем в эту задачу не входят.
