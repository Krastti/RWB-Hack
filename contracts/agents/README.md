## Схемы и публичный интерфейс

Канонический источник — статические JSON Schema в `v1/`; они не зависят
от Python-моделей конкретного агента. Все публичные объекты закрыты для
неизвестных полей. `$id` использует зарезервированный домен `.invalid` только
как идентификатор. Сетевой загрузки схем нет.

| Схема | Назначение |
|---|---|
| [common](v1/common.schema.json) | Повторно используемые типы: UUID, FR, вопросы, допущения, evidence, usage, diagnostics и metadata артефакта; самостоятельно не валидируется |
| [agent-input](v1/agent-input.schema.json) | Контекст одного вызова агента и лимиты |
| [agent-result](v1/agent-result.schema.json) | Результат вызова, артефакты, вопросы, метрики и диагностика |
| [artifact](v1/artifact.schema.json) | Metadata и ровно один источник содержимого: content либо storage_ref |
| [analysis-input](v1/analysis-input.schema.json) | Текст бизнес-требований, подтверждённые ответы и ссылки на предыдущий анализ/регламент |
| [requirements](v1/requirements.schema.json) | Структурированный requirements.json: факты, FR/NFR, роли, сценарии, критерии, риски, допущения и вопросы |
| [questions](v1/questions.schema.json) | questions.json одной ревизии |
| [architecture](v1/architecture.schema.json) | Компоненты, границы, решения и ссылки на согласуемые API/data/UI/plan артефакты |
| [generation-plan](v1/generation-plan.schema.json) | Зависимости заданий, владельцы выходов, входные references и версия контракта |
| [manifest](v1/manifest.schema.json) | Неизменяемый снимок файлов и ссылки на traceability |
| [traceability](v1/traceability.schema.json) | FR → файлы, API operations, entities, screens либо явное отсутствие реализации |

Подробные схемы содержимого OpenAPI, data-model.json и ui-spec.json здесь
не изобретаются: их определяют профиль и архитектурные задачи A-06/A-07/A-08.
В C-02 фиксируются типизированные references на эти артефакты. Примеры их
содержимого в ответе архитектора иллюстрируют связи, не заменяют полный контракт.
Полный system-analysis.md — Markdown по шаблону A-02, а не ещё один JSON payload.

## AgentInput

Обязательные поля соответствуют §10 спецификации:
`schema_version`, `run_id`, `stage_id`, `attempt`, `input_artifact_ids`,
`contract_version`, `profile_id`, `limits`.

- `schema_version="1.0"` задаёт wire-формат C-02.
- `contract_version` — версия предметных контрактов текущего проекта, например
  `"1"` или согласованный SHA. Она не равна версии модели или номеру попытки.
- `attempt` — положительный номер одного исполнения этапа. История, автоматические
  retry и ручные перезапуски сохраняются orchestrator; агент их не сбрасывает.
- `input_artifact_ids` — уникальные UUID неизменяемых входов. Worker проверяет
  принадлежность запуску/пользователю, версию, checksum и разрешает ссылки через
  storage adapter. Это не URL, пути на сервере или команды.
- `stage_id`/`profile_id` имеют расширяемые идентификаторы; допустимые для запуска
  значения и права определяет конфигурация сервера. В примерах: analysis,
  architecture, frontend, backend. Schema не позволяет пользователю выбрать
  произвольный исполняемый инструмент.
- `limits` требует max_calls и max_output_tokens; timeout_seconds и
  max_critical_questions при необходимости передаются из профиля. Начальное
  значение лимита критичных вопросов — 3 по спецификации; изменение конфигурацией
  не требует изменения схемы. Default не подставляется JSON Schema автоматически.

Исходный бизнес-текст передаётся через разрешённый входной артефакт
`analysis-input`. Дополнительные предметные анкеты не нужны. Ответы содержат
UUID вопроса и value; непустой пакет требует previous_requirements_artifact_id
и положительной questions_revision. Регламент — отдельный артефакт, выбранный
сервером, а не инструкция из бизнес-текста. Все эти references должны входить
в разрешённый набор input_artifact_ids вызова.

## AgentResult и уточнения

Результат повторяет run_id/stage_id/attempt/contract_version вызова и содержит
status, output_artifacts, questions, assumptions, usage, diagnostics.

| status | Значение и обязательное условие |
|---|---|
| succeeded | Узел подготовил результат: минимум один артефакт, нет ошибок diagnostics и нерешённых обязательных вопросов |
| waiting_for_input | Есть хотя бы один вопрос с required=true без answer; частичный результат сохраняется |
| failed | Есть diagnostics с severity=error; можно вернуть ранее проверенные частичные артефакты |
| cancelled | Остановка на безопасной границе с диагностикой причины |
| skipped | Этап неприменим с диагностикой причины |

`pending` и `running` — состояние исполнения у orchestrator, не завершённый
AgentResult. Исчерпание бюджета возвращается как failed с диагностикой,
например BUDGET_EXCEEDED; состояние запуска budget_exceeded устанавливает
orchestrator по C-03. Успех узла не означает completed всего проекта.

Question использует поля существующего API: `question_id` (UUID), `question`,
`reason`, `required`, `related_fr_ids`, необязательный `answer`. `required=true`
означает критичный вопрос, без ответа нельзя продолжать зависимый этап.
Пустой ответ запрещён, отсутствие ответа представляется **отсутствием поля**,
а не null. UUID стабилен при повторе и уточнении. Новые вопросы повышают ревизию;
повторная передача ответа на ту же ревизию не создаёт новый вопрос.

Ответы принимает API только для текущей ревизии своего запуска. Worker сверяет
их с сохранёнными вопросами; модель не может подтверждать ответы сама.
Схема требует правильную форму, а актуальность ревизии, лимит вопросов за цикл,
смысл критичности и фактические переходы проверяют API/orchestrator.

Список обязательных артефактов проверяется профилем: для успешного анализа нужны
requirements.json, questions.json и docs/system-analysis.md; для архитектора —
architecture.json, contracts/openapi.yaml, data-model.json, ui-spec.json и
generation-plan.json. Неполный результат нельзя объявлять успешным для профиля
только потому, что общий AgentResult прошёл валидацию.

## Артефакты и references

Metadata совпадает по именам с Artifact в API: artifact_id, attempt_id, path,
kind, media_type, version, schema_version, author_agent, checksum, size_bytes,
related_fr_ids. Внутренний Artifact дополнительно содержит ровно одно из:

- `content`: строка точных байтов текстового файла после UTF-8 кодирования;
- `storage_ref`: непрозрачный относительный ключ доверенного storage adapter.

content предназначен для текста; бинарные файлы передаются через storage_ref
с checksum и размером фактических бинарных байтов.

Artifact reference в architecture/manifest — metadata без content/storage_ref.
`kind` — смысл (`requirements`, `system_analysis`, `openapi`, `source` и т.д.);
`media_type` — MIME (`application/json`, `text/markdown` и т.д.). Это разные поля.
Checksum — SHA-256, 64 строчных hex-символа, без префикса. Размер — число UTF-8
байтов, не символов. JSON/переводы строк/пробелы перед хешированием не нормализуются.

UUID, attempt_id, версия и ссылки резервируются/проверяются worker; размер и
checksum вычисляются по фактическим байтам, а не принимаются на веру от LLM.
Переход к storage_ref не меняет содержимое, checksum или artifact_id.
Идентификатор существующего артефакта не переиспользуется для других байтов;
изменение файла создаёт новый artifact_id и увеличивает version логического пути.

Paths — непустые относительные POSIX-пути из ASCII букв, цифр, `_`, `-`, `.`,
со `/` между сегментами. Запрещены абсолютные пути, `.`/`..` как сегмент,
двойной `/`, завершающий `/`, backslash, drive letters, URL и percent encoding.
Это консервативный набор для первого профиля. Для каталогов используется тот же
формат без завершающего `/`. Проверка симлинков, границ run directory, доступа
к storage_ref и запрета выполнения файлов остаётся задачей storage/worker.

Manifest не включает собственный manifest.json в artifacts: его checksum
иначе зависел бы от него самого. Файл manifest.json включается в экспорт отдельно.
Traceability перечисляет каждый FR, включая unimplemented с объяснением.
readiness=prepared означает полноту подготовки по профилю, не PASS тестов,
сборки или deploy. Пример manifest помечен partial: исходники ещё не созданы.

## Usage и diagnostics

`usage.calls` равно длине model_calls. Каждый вызов имеет уникальный call_id,
model, outcome, input_tokens/output_tokens и duration_seconds. Реальная попытка
обращения учитывается и при ошибке; отказы до обращения имеют calls=0.
Если provider не вернул usage, токены этого вызова равны null. Сводные токены
равны сумме только когда известны все значения; иначе null, без фиктивных нулей.
Для нуля вызовов известная сумма — 0. Сохранение полученного usage при ошибке
парсинга ответа обязательно для вызывающего кода.

usage.duration_seconds — время одного этапа без ожидания человека. Оно не обязано
равняться сумме длительностей вызовов, например при параллельных обращениях.
В API Metrics: input_tokens → tokens_in, output_tokens → tokens_out,
calls → model_calls, секунды → duration_ms. История attempts и ручных уточнений
считается по сохранённым событиям, не выводится из номера последней попытки.

Diagnostic: code, безопасное message, severity, retryable, related_fr_ids,
при необходимости artifact_id. retryable — разрешённость обсуждения повтора,
не команда выполнить его. Raw prompt, provider body, traceback и секреты в
diagnostics не включаются. Схема не может обнаружить произвольный секрет в строке:
очистку и контроль входов обеспечивает платформа.

## Проверка из чистого окружения

Python 3.11+. Из корня репозитория:

```sh
python3 -m venv contracts/agents/.venv
source contracts/agents/.venv/bin/activate
python -m pip install -r contracts/agents/requirements.txt
python contracts/agents/validate.py --check
```

Ожидается:

```text
OK: 11 schemas, 22 examples, 4 linked bundles, 1 snapshot; offline
```

Отдельный документ:

```sh
python contracts/agents/validate.py agent-result contracts/agents/examples/agent-result.waiting.json
```

CLI возвращает 0 при успехе, 1 при нарушении контракта, 2 при неверных аргументах.
Все `$ref` разрешаются из локального реестра; FormatChecker включён, UUID и даты
действительно проверяются. Интернет используется только для установки зависимостей.
Адаптер LLM должен подготовить поддерживаемую provider форму схемы, включая
разрешение `$ref`; наличие C-02 не подтверждает поддержку Draft 2020-12 сервером модели.

Проверяются метасхемы и все ссылки, индекс примеров, контексты input/result,
FR/role/question IDs, критерии приёмки, evidence, usage, inline SHA-256/размер,
metadata references, DAG и владельцы выходов generation-plan, snapshot/traceability.
Список соответствий файлов и схем — [examples/index.json](examples/index.json).
Примеры, тексты Markdown и метрики написаны вручную, это не результаты LLM.
Они показывают форму и согласованность, а не доказывают правильность анализа
или работоспособность сгенерированного приложения.

Для отдельного документа проверяются только доступные внутри него условия.
`--check` дополнительно проверяет связанные примеры. Внешние артефакты,
доступ/владение, обязательные файлы профиля, стабильность смысла FR и готовность
полного продукта подтверждает runtime. storage_ref валидируется как ключ, его
содержимое не загружается. Полные OpenAPI/data/UI schemas здесь не проверяются.

## Версионирование и принятие

Набор v1/ описывает schema_version=1.0. До принятия это согласуемый проект;
после принятия формат не менять без новой версии и примеров миграции.
Закрытые объекты означают, что даже новое необязательное поле может нарушить
совместимость со старым потребителем. Пояснения можно исправлять без изменения
формата; изменение допустимых документов требует отдельной версии/согласования.
contract_version предметного проекта меняет архитектор до запуска потребителей.

Перед merge нужны review и согласование с #75/#76/#77/#78 и владельцем C-03.
Результат локальной проверки — необходимое свидетельство, но не независимое
одобрение и не автоматическое принятие контракта.
