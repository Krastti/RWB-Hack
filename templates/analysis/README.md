## Что возвращает модель

`requirements` — неизменённый C-02 payload версии 1.0. Все сведения заказчика
содержат evidence из исходного текста или подтверждённого ответа. Допущения
хранятся отдельно с reason; критичные вопросы — с UUID/required/reason/FR.
Для отсутствующего ответа поле answer опускается. Неизвестный факт не дополняется
догадкой и не помечается неприменимым автоматически.

`design_notes` — шесть предварительных разделов, которых нет отдельными полями
в requirements C-02. Каждый имеет `status`, обычный текст и ссылки на FR/ASM/вопросы.
`proposed` требует минимум один ASM; `needs_clarification` — реальный неотвеченный
обязательный вопрос; `not_applicable` — конкретное предметное обоснование.
Их schema_version относится только к внутреннему draft A-02. Эти заметки
**не являются** архитектурными JSON/OpenAPI-контрактами A-05–A-08.

Рендерер выводит факты из одного requirements payload и помещает предложения
в отдельные разделы с явным статусом. Пользовательский/model текст экранируется:
он не может добавить собственный заголовок или HTML в Markdown. Неприменимые
разделы сохраняются с причиной. Пустой список фактов обозначает отсутствие
сведений во входе; это не доказательство отсутствия предметной функции.

Успешный вызов LLM сам по себе не принимается как корректный анализ:
`generate_analysis` проверяет draft до возврата успеха. Несогласованные ссылки,
неподтверждённые цитаты/ответы и нарушенная история дают `ANALYSIS_INVALID_DRAFT`
с сохранением расхода вызова. Эта проверка не заменяет оценку смысла требований.

Регламент организаторов необязателен и передаётся отдельно по разрешённому
analysis_rules_artifact_id. Без него используется базовая структура PDF;
с ним нельзя автоматически заявлять полное соответствие: дополнительные правила
и их конфликт с текущим шаблоном требуют проверки/обновления версии шаблона.

## Примеры и границы

Первый вход — заявки на ремонт с неясными правами удаления. Пример сохраняет
FR-001–FR-003, один обязательный вопрос и предварительный анализ всех разделов.
После подтверждённого ответа «Удаление запрещено всем ролям.» сохраняются старые
IDs и questions_revision=1, добавляется FR-004 и снимается блокер удаления.

| Запуск | Контекст | Предметный вход | Ответ модели |
|---|---|---|---|
| Первичный | [agent-input.json](examples/agent-input.json) | [analysis-input.json](examples/analysis-input.json) | [draft.json](examples/draft.json) |
| Возобновление | [agent-input.resume.json](examples/agent-input.resume.json) | [analysis-input.resume.json](examples/analysis-input.resume.json) | [draft.answered.json](examples/draft.answered.json) |

UUID в примерах иллюстративны. `previous_requirements_artifact_id` во втором
входе разрешается в `draft.json.requirements`; остальные input IDs обозначают
соответствующий analysis-input. Это fixtures интерфейса, не сохранённые артефакты
реального запуска и не реальные ответы LLM. `example.py` не записывает их в storage.

A-03 отвечает за стабильность смысла FR, сохранение UUID/revisions между
перезапусками, смысловую проверку evidence, историю попыток, usage и упаковку
трёх обязательных выходов. Архитектор фиксирует финальные API/data/UI; при изменении
контрактов повышает contract_version. Документационный агент не переписывает
принадлежащий аналитику system-analysis.md. Возврат несогласованности владельцу
создаёт новую ревизию, а не тихую правку снимка сборщиком.
