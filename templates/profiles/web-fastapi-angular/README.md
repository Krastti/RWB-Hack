# Профиль `web-fastapi-angular` — C-05

Задача: [#55](https://github.com/Krastti/RWB-Hack/issues/55).
Версия профиля: **1.0.0**, формат профиля: **1.0**.
Статус: предложение для review; согласование потребителей фиксируется при принятии PR.
Основание: §3, §10–12 [спецификации](../../../docs/project-specification.md),
[роадмап](../../../docs/development-roadmap.md) и [C-02](../../../contracts/agents/README.md).
Прочитанная база `main`: `ef1956c958ef64c8784ce0558c53269bea25142f`.

Профиль описывает **генерируемый проект**. Это контракт для A-02, A-05–A-19,
A-20 и B-14/B-20, а не реализация агентов, шаблон приложения или готовый pipeline.
F-01 может использовать соглашения Angular/Bootstrap для интерфейса платформы; дерево результата,
API и конфигурация генерируемого проекта остаются отдельными от платформы.

## Публичный интерфейс и версии

- [profile.json](profile.json) — канонические значения стека, обязательных путей,
  владельцев, лимитов и UI Kit. Этот README — нормативные правила их интерпретации.
- [profile.schema.json](profile.schema.json) — JSON Schema Draft 2020-12 формата
  профиля. Общие типы путей и лимитов переиспользуются из C-02, без копирования схем.
- [examples/agent-input.frontend.json](examples/agent-input.frontend.json) — вход
  frontend-агента по существующему `agent-input.schema.json`.
- [examples/generation-plan.json](examples/generation-plan.json) — пример плана
  после фиксации архитектуры, с непересекающимися выходами.

Сервер разрешает `profile_id=web-fastapi-angular` в этот каталог из своего allowlist.
Он загружает профиль, проверяет схему и правила ниже, фиксирует его версию,
SHA-256 точных байтов и эффективные лимиты в неизменяемом контексте запуска.
Пользователь передаёт `profile_id`, но не путь к шаблону, команды или новые права.
В C-02 нет полей `profile_version`/`profile_checksum`: не добавлять их в закрытые
AgentInput/Artifact/Manifest. Их хранение — обязанность контекста orchestrator.

| Версия | Смысл |
|---|---|
| `profile_version=1.0.0` | Конкретный набор правил и defaults этого профиля |
| `profile.json.schema_version=1.0` | Формат конфигурации профиля |
| C-02 `schema_version=1.0` | Формат AgentInput, AgentResult, Artifact, анализа, архитектуры, плана, манифеста и traceability; пути схем указаны в `contracts.schemas` |
| `contract_version`, например `"1"` | Версия предметных API/данных/UI одного проекта, назначаемая архитектором |
| Artifact `version`, например `1` | Ревизия содержимого конкретного логического пути |
| OpenAPI `3.1.0` | Версия формата `contracts/openapi.yaml`; `info.version` соответствует предметному контракту |

`data-model.json` и `ui-spec.json` обязательны, но детальные схемы их содержимого
в текущем C-02 ещё не определены: владельцы — A-07 и A-08. Не считать
`Artifact.schema_version=1.0` доказательством валидации этих payloads. Архитектор
фиксирует версии их форматов вместе с OpenAPI до генерации; потребитель без
поддержки согласованной схемы останавливается с диагностикой. Иллюстративные
payloads C-02 не заменяют эти контракты. A-06 отвечает за предметный OpenAPI.

Изменение правил, обязательных файлов или defaults выпускается новой версией
профиля; несовместимое изменение повышает major и согласуется с потребителями.
Изменение формата требует новой schema_version и схемы. Редактура пояснений
без изменения поведения не меняет версию. Уже начатый запуск использует свой
снимок; повтор не подхватывает новый профиль. Точные версии библиотек фиксируют
A-10/A-12 в зависимостях шаблона; этот контракт не заявляет проверенную совместимость
конкретных релизов библиотек и не разрешает зависимости `latest`.

## Стек и дерево результата

Frontend: Angular 22, standalone-компоненты, TypeScript в strict mode, Bootstrap 5.3 и SCSS. Angular CLI, Router, Reactive Forms, HttpClient и RxJS. Backend: FastAPI, Pydantic,
SQLAlchemy, PostgreSQL. Для миграций выбран Alembic как соглашение этого профиля,
а не требование организаторов и не изменение миграций backend платформы.
Kotlin/Compose и PostGIS относятся к отдельным расширениям X-01–X-06.
Kafka допустима только при обоснованном предметном требовании и описанном контракте.

## Артефакты и условие готовности

| Этап / владелец | Обязательный результат |
|---|---|
| `analysis` | requirements.json, questions.json, docs/system-analysis.md |
| `architecture` | architecture.json, contracts/openapi.yaml, data-model.json, ui-spec.json, generation-plan.json |
| `frontend` | Исходники экранов, реальный API client, theme и конфигурация frontend |
| `backend` | FastAPI API, DTO, предметные сервисы, SQLAlchemy-модели и работа с PostgreSQL |
| `migrations` | Alembic env, начальная миграция и инструкция применения |
| `integrations` при необходимости | Контракты, адаптеры и явно обозначенные mock внешних систем |
| `documentation` | Шесть документов docs, README по фактическому дереву |
| `assembly` | manifest.json, traceability.json и .gitignore |

Все файлы результата получают metadata C-02: `artifact_id`, `attempt_id`, `path`,
`kind`, `media_type`, `version`, `schema_version`, `author_agent`, `checksum`,
`size_bytes`, `related_fr_ids`. `kind` берётся из профиля для фиксированных путей;
для остальных исходников — `source`, миграций — `migration`, настроек —
`configuration`, документации — `documentation`. MIME описывает фактические байты:
JSON — `application/json`, Markdown — `text/markdown`, YAML — `application/yaml`.
JSON в openapi.yaml допустим как подмножество YAML с `application/json`, как в C-02.

Checksum — SHA-256 точных байтов, 64 lowercase hex; размер — байты UTF-8 для
текста. Worker вычисляет их сам. Для изменения содержимого резервируются новый
artifact_id и следующая version пути. Устаревшая попытка не перезаписывает результат.

Сборщик A-19 должен подтвердить:

1. Все обязательные и обусловленные интеграциями файлы присутствуют, а выходы
   плана соответствуют правам; пути уникальны, входные references разрешены.
2. C-02 payloads соответствуют указанным схемам; OpenAPI, data/UI payloads —
   своим согласованным форматам. Все зависимые результаты используют одну
   contract_version. Смена API/модели/UI требует новой версии и инвалидирует
   зависимые артефакты; генераторы не меняют контракт самостоятельно.
3. FR существуют в requirements; traceability содержит для каждого FR ссылки
   на файлы, операции API, сущности, экраны либо явный статус отсутствия реализации.
   Служебные файлы могут иметь пустой `related_fr_ids` с объяснением в документации.
   Статус частичного/непокрытого FR и его причина остаются видимыми; фиктивные
   файлы и mock основной логики не превращают его в реализованный.
4. manifest перечисляет точные metadata всех выдаваемых файлов, включая
   traceability. **manifest.json не включает сам себя**: его hash хранится снаружи
   снимка. Сам файл остаётся обязательным и учитывается в файловом бюджете.
5. Нет блокирующих `unresolved_items` с severity=error. Если обязательный результат
   отсутствует, контракты не поддержаны или критичный вопрос не решён, снимок
   `partial`; нельзя выставлять `prepared`/`completed` только по валидности JSON.

`prepared` и состояние запуска `completed` означают «проект подготовлен».
Они не подтверждают тестирование, сборку, сканирование безопасности или deploy.
Непокрытые FR сохраняют явный статус по C-02; их допустимость определяется
принятыми границами проекта, а не скрытым решением генератора.

system-analysis.md охватывает назначение, границы, роли и права, сценарии, FR/NFR,
компоненты, данные, API, события/интеграции, входные ограничения, ошибки,
критерии приёмки, допущения и вопросы. README/development-guide описывают реальные
зависимости, переменные, подготовку PostgreSQL, миграции и команды разработки;
не заявляют, что эти команды уже проверены. limitations отдельно перечисляет
допущения, неподдержанные требования и внешние mock.

## UI Kit и правила кода

Bootstrap 5.3 подключается через `frontend/src/styles.scss`; тема задаётся SCSS-переменными
и CSS custom properties. Приложение использует standalone-компоненты Angular,
Router, Reactive Forms, HttpClient и RxJS. Angular CLI управляет сборкой; не добавлять
второй UI Kit. Layout и оформление адаптируются из SB Admin Angular с сохранением
MIT-лицензии в THIRD_PARTY_NOTICES.md. Старые зависимости Angular 11/Bootstrap 4
и Pug из исходного шаблона не переносятся. Точные совместимые версии фиксируются
в package.json и package-lock.json; Node.js 24.15+ и TypeScript 6.0.x.
Пользовательский виджет допустим для предметного взаимодействия; его назначение
и доступность отражаются в UI spec. Иконкам-кнопкам нужны подписи.

Для каждого экрана UI spec связывает FR, роли, действия, `operationId` из OpenAPI
и компоненты Angular/Bootstrap. Обязательны состояния loading, empty, error, forbidden, success;
для неприменимого состояния фиксируется причина. Обеспечить клавиатурную навигацию,
видимый focus, labels и связанные сообщения валидации. Для запросов предусмотреть
повтор после ошибки соединения; кнопки блокируются на время отправки.
Адаптивные ориентиры — ширины 360, 768 и 1280 px: без потери ключевых действий;
для таблиц допускается локальная прокрутка. Это правила генерации, не отчёт UI-тестов.

Frontend использует типизированный клиент по OpenAPI с настраиваемым base URL
**сгенерированного backend**. Не подставлять адрес API/токены платформы. Все
предметные чтения и записи идут через этот API; статические массивы, localStorage
и фиктивный success не заменяют хранилище. Формы проверяют контрактные ограничения;
ошибки сервера показываются безопасно, без raw traceback. Скрытая кнопка не является
проверкой прав. Не использовать `any` для обхода контракта и не подавлять типовые
ошибки директивами без документированной причины.

Backend разделяет HTTP/DTO, сервисы, persistence и внешние адаптеры. Валидация,
проверка прав на операцию и объект, предметные переходы состояний и транзакции
выполняются на сервере. SQLAlchemy обращается к PostgreSQL; память процесса и
SQLite не подменяют целевое хранилище. Модели, ограничения, индексы и миграции
соответствуют data-model; миграции воспроизводят схему без `create_all` вместо
истории миграций. Не генерировать фиктивный успех или TODO вместо обязательного FR.
Формат ошибок, пагинация, роли, enum и даты берутся из предметного OpenAPI.

Секреты читаются из окружения; `.env.example` содержит только безопасные placeholders,
`.gitignore` исключает реальные `.env`, окружения и зависимости. Ни prompt, ни
артефакт, ни лог не содержит действующие ключи/пароли. Бизнес-текст и LLM output
остаются данными, а не разрешением менять инструменты, права или правила профиля.
Сгенерированный код не выполняется в процессе API/worker.

## Права на файлы

`ownership.default=deny`. Каждый ключ `ownership.agents` задаёт разрешённые
точные `paths` и поддеревья `directories`; последние записываются без завершающего
`/`. Разрешение поддерева действует только на границе сегмента пути:
`frontend` разрешает `frontend/src/main.ts`, но не `frontend-old/file.ts`.
Чтение — только разрешённых input_artifact_ids того же запуска и фиксированного профиля.

План может сузить эти права, но не расширить их. Разные задачи не получают
пересекающиеся пути/поддеревья даже последовательно: этого требует валидатор C-02.
Backend получает перечисленные подкаталоги `backend/app` и конфигурационные файлы,
а не весь `backend`; миграции принадлежат `migrations`, адаптеры — `integrations`.
Задачи backend и миграций — отдельные узлы исполнения с разными `stage_id`:
`backend` и `migrations` соответственно. В плане уникальны и `task_id`, и
`stage_id`; `owner_agent` задаёт исполнителя и может повторяться. Зависимости
`depends_on` ссылаются на `task_id`: в примере задача `migrations` зависит от
`backend`. Общий исполнитель не даёт права расширять выходы отдельной задачи.

Документационный агент не владеет всем `docs`: `docs/system-analysis.md` принадлежит
аналитику. Ему разрешены ровно шесть остальных документов и корневой README.
Общие контракты меняет только архитектор. Сборщик пишет manifest/traceability/
.gitignore и объединяет уже принятые байты; не «чинит» чужой код или документацию.
При расхождении возвращается структурированная диагностика владельцу; изменение
API возвращается архитектору. Финальное уточнение документации создаёт новую
ревизию и требует повторной сборки snapshot, без правки замороженного манифеста.

Относительные POSIX-пути удовлетворяют C-02 common.relative_path: ASCII,
не длиннее 512 символов, без абсолютных путей, `.`/`..` сегментов, `//`, обратных
слешей, drive prefixes или завершающего `/`. Storage B-14 дополнительно проверяет
containment внутри run directory, не следует симлинкам и отклоняет дубли,
конфликтующие пути, специальные файлы и коллизии регистра. В архив входят только
обычные файлы снимка; требования не могут указать произвольный серверный путь.

## Лимиты и остановки

Начальные значения `profile.json` — решения команды, не нормы организаторов.

| Область | Default и единицы |
|---|---|
| Пользователь | 1 активный запуск; queued/running/waiting_for_input/cancelling занимают слот |
| Запуск | 60 вызовов модели, 300 000 входных и 180 000 выходных токенов, 3600 секунд активного исполнения |
| Попытка агента | 10 вызовов, 30 000 выходных токенов, 600 секунд активного исполнения |
| Один вызов модели | 120 секунд, дополнительно ограничен остатком времени попытки/запуска |
| Автоматические повторы | До 2 на этап за весь запуск: первая попытка + не более 2 повторов |
| Уточнения | До 2 раундов ожидания, до 3 обязательных вопросов в раунде |
| Результат | 500 файлов, 1 MiB на файл, 25 MiB суммарно; 1 MiB = 1 048 576 байтов |

`limits.agent` передаётся в AgentInput.limits. `limits.run`, `model_call`,
`artifacts` остаются серверной политикой: не добавлять их полями закрытой C-02
схемы. Агенту назначается минимум его default, разрешённой серверной настройки
и ещё доступного бюджета запуска. Лимиты положительны; max_calls допускает 0
для детерминированного этапа. При исчерпании токенов не создавать AgentInput с
нулевым max_output_tokens — остановить запуск до вызова.

Администратор может менять defaults разрешённой конфигурацией; пользовательский
текст их не меняет. Эффективные значения фиксируются до старта. Обычный retry не
сбрасывает usage, число раундов и автоматических повторов; рестарт worker тоже.
Для ручного продолжения `budget_exceeded` необходимо явное увеличение разрешённого
лимита с сохранением накопленного расхода. Автоповторов по-прежнему не больше двух.

Вызовы и токены учитываются по всем попыткам, включая ошибочные и отменённые;
уточнения и повторная генерация также расходуют общий бюджет. Перед параллельной
отправкой orchestrator атомарно резервирует calls и верхние границы токенов,
чтобы сумма выданных бюджетов не превышала остаток. Входные токены ограничиваются
измерением/консервативной оценкой до отправки. Неизвестный provider usage остаётся
null по C-02, не превращается в ноль: резерв удерживается, а при невозможности
безопасного учёта дальнейшие платные вызовы останавливаются с диагностикой.

Срок запуска считается по wall-clock интервалам активного исполнения, без двойного
суммирования параллельных агентов; очередь и waiting_for_input в него не входят.
Ожидание пользователя не держит открытым LLM-вызов. Лимит попытки начинается при
её запуске. Срок модельного вызова не больше оставшихся сроков попытки и запуска.
Файловый бюджет относится к выбранному снимку (включая manifest); хранение истории
попыток дополнительно ограничивается политикой storage. Размер проверяется до записи.

При общем лимите сохраняются принятые частичные результаты и возвращается
`AgentResult.status=failed` с диагностикой `BUDGET_EXCEEDED`; orchestrator переводит
Run в `budget_exceeded`. Таймаут/ошибка отдельного вызова допускает ограниченный
retry только при `retryable=true` и оставшемся бюджете. Ошибки схемы, входа и
критичные вопросы не повторяются вслепую. Незавершённый файл не выдаётся как готовый.

После двух раундов нерешённый критичный вопрос не становится допущением:
этап останавливается с диагностикой `CLARIFICATION_LIMIT_REACHED`, Run — `failed`.
Возобновление требует явного решения пользователя. Коды диагностик здесь —
расширяемые значения C-02, не новые HTTP-коды или самостоятельно введённые
состояния C-03. Логику переходов реализует orchestrator.

## Границы mock-интеграций

Mock разрешён только на границе **недоступной внешней системы**. Адаптеры real/mock
реализуют один контракт; выбор режима явный через конфигурацию и отражён в
limitations. При недоступности real запрещён незаметный fallback на mock-success.

Для каждой интеграции описать назначение, FR, операции, поля запросов/ответов,
ошибки, таймауты, авторизацию без секретов, правила идемпотентности и повторов.
Для событий также нужны ID, версия, timestamp, предметная схема и обработка дублей.
Mock использует синтетические данные, детерминированные успешные и ошибочные
сценарии. Пример: внешний геокодер может вернуть заданные координаты; создание
предметной сессии, проверка владельца, переход статуса и запись в PostgreSQL
всё равно выполняются настоящим backend.

Нельзя mock-ответами подменять основные API, авторизацию/права, persistence,
предметные расчёты или переходы состояний. Если обязательная интеграция не может
быть описана безопасно, фиксируются вопрос/диагностика и непокрытые FR.

## Пример использования и локальная проверка

Примеры написаны вручную и используют идентификаторы входных артефактов из
[примеров C-02](../../../contracts/agents/examples/architecture.json).
Worker разрешает UUID в реальные артефакты своего запуска; копировать эти UUID
в production-запуск нельзя. План показывает продолжение после аналитика и
архитектора без внешних интеграций, а не полный успешный результат приложения.
При материализации плана input_artifact_ids дополняются точными references
доступных результатов зависимостей до вызова соответствующей задачи.
Документация может готовить черновик параллельно; в примере её финальный вызов
следует после кода, чтобы не создавать цикл docs → manifest → docs.

Потребитель загружает профиль по ID, замораживает архитектурные контракты,
сужает выходы плана до разрешённых путей и подставляет эффективные `limits.agent`
в AgentInput. После каждого успешного узла worker сохраняет артефакты и checkpoint;
сборщик использует правила готовности выше. C-05 описывает этот интерфейс, не
предоставляет исполняемый loader/orchestrator или проверку готовности snapshot.

Из корня репозитория в Python-окружении с зависимостями C-02:

```sh
python contracts/agents/validate.py --check
python contracts/agents/validate.py agent-input templates/profiles/web-fastapi-angular/examples/agent-input.frontend.json
python contracts/agents/validate.py generation-plan templates/profiles/web-fastapi-angular/examples/generation-plan.json
python - <<'PY'
import json
from pathlib import Path
from jsonschema import Draft202012Validator, FormatChecker
from referencing import Registry, Resource

root = Path('templates/profiles/web-fastapi-angular')
schemas = [json.loads(p.read_text()) for p in Path('contracts/agents/v1').glob('*.schema.json')]
schema = json.loads((root / 'profile.schema.json').read_text())
schemas.append(schema)
registry = Registry().with_resources((s['$id'], Resource.from_contents(s)) for s in schemas)
Draft202012Validator.check_schema(schema)
Draft202012Validator(schema, registry=registry, format_checker=FormatChecker()).validate(
    json.loads((root / 'profile.json').read_text())
)
print('OK: profile format; local schema registry')
PY
```

`$id` на `.invalid` — идентификаторы, не сетевые адреса; схемы разрешаются локально.
Эти команды проверяют формат профиля и совместимость примеров. Семантические
проверки прав, обязательных файлов, согласованности лимитов и фактического
результата принадлежат потребителям профиля. CI/CD, контейнеризация, тесты
генерируемого приложения, security scanning и deploy в эту задачу не входят.


### Budget retry stabilization policy

C-01 Retry can raise max_calls/max_output_tokens only. Run.stop_reason uses
MAX_CALLS or MAX_OUTPUT_TOKENS for these causes; required_limits includes the
reservation for next work, and the cause-specific limit must increase. Cumulative
usage and frozen profile are preserved; authorization is mandatory. MAX_INPUT_TOKENS
and RUN_TIMEOUT (active Run execution time), and unknown causes, reject public
retry with HTTP 409 RETRY_NOT_SUPPORTED without effects. UI hides this retry.
The existing elapsed duration_ms includes wall-clock waiting and is not proof of
active-time exhaustion. A single model_call.timeout_seconds is a request deadline,
not RUN_TIMEOUT; it follows the existing failed-attempt policy. No API for changing
input/time limits is introduced. Accounting producers must supply the cause; an
unknown cause never grants continuation.
